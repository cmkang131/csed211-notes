데이터 파트 시작

오늘의 범위 : Array(배열) 먼저, 그다음 struct

지금까지는 기본 data type을 하나씩만 다룸 : 포인터 8byte, long 8byte, int 4byte(8byte의 절반), short 2byte, char 1byte

  • 교수님 평가 : Data 파트는 control flow, procedure 파트보다 쉬운 부분

이제는 같은 종류의 값을 모아 저장하는 array, 서로 다른 type을 묶는 struct를 다룸 → 순서는 array 먼저, struct는 그다음

아키텍처가 하는 일은 최소한

  • 64bit register를 통째로, 절반, 1/4 … 로 쓸 수 있어서 8, 4, 2, 1 byte짜리 기본 type을 표현할 수 있을 뿐
  • "int 배열"을 직접 표현하는 하드웨어 기능은 없음 → 배열 접근은 전부 offset 계산
  • 앞에서 배운 lea와 주소 지정 모드 : base, index, scale(원소 크기), displacement로 특정 index의 주소를 계산
  • 이 주소 계산이 안전하게 만들어지도록 하는 것은 컴파일러의 몫

정리하면 "기준(base) 주소가 어디이고 offset이 얼마인가"로 귀결 → 이번 파트는 포인터/주소 산술로 1차원 배열, 다차원 배열, struct에 접근하는 방법

1차원 Array(배열)

Array(배열) 할당 : T N[L]

T N[L]; : data type T, 길이 L, 이름 N인 배열

  • 메모리에 연속된 L * sizeof(T) byte를 할당 → 크기 = 원소 개수 × 원소 크기라서 계산이 쉬움

슬라이드 예 (시작 주소를 x라 하면)

  • char string[12] : 1 × 12 = 12 byte, 원소 주소 x, x+1, … x+11
  • int val[5] : 4 × 5 = 20 byte, 원소 시작 주소 x, x+4, x+8, x+12, x+16
  • double a[3] : 8 × 3 = 24 byte, 원소 시작 주소 x, x+8, x+16
  • char *p[3] : 포인터 8 × 3 = 24 byte, 원소 시작 주소 x, x+8, x+16

그림의 굵은 경계선이 원소 하나의 경계 → int는 간격 4byte, double과 포인터는 간격 8byte

  • 간격이 일정해서 특정 원소의 위치를 곱셈 한 번, 덧셈 한 번으로 계산할 수 있음

Array(배열) 접근과 byte 배치

int val[5] = 3, 7, 6, 7, 3 → 시작 주소 x부터 한 원소가 4byte

메모리에는 03 00 00 00 07 00 00 00 06 00 00 00 07 00 00 00 03 00 00 00 순서로 저장됨

교수님 질문 : 정수 3은 4byte 칸의 왼쪽 byte에 들어갈까, 오른쪽 byte에 들어갈까?

  • 답 : little endian → 가장 낮은 자리(least significant byte)가 가장 낮은 주소에 놓임
  • Intel이 little endian이라서 슬라이드의 byte 열에서 03이 맨 왼쪽(낮은 주소)에 있음

Array(배열) 이름과 Pointer(포인터) 산술

C에서는 식에 따라 저장된 값을 가리킬 수도 있고, 메모리 위치(주소) 를 가리킬 수도 있음

val[4] (int, 값 3) : index로 값을 읽음, 마지막 원소

val[5] (int, 값 ??) : 범위를 벗어남 → 값을 알 수 없음

  • (보충) 주소로는 x+20, 배열 바로 다음 칸 → C와 하드웨어는 범위를 검사하지 않음

val (int *, 값 x) : 배열 이름 자체가 첫 원소의 주소

val+1 (int *, 값 x+4) : 이름에 정수를 더하면 원소 크기를 곱해서 주소가 늘어남 → 한 원소 뒤의 주소

  • int 배열이라 +1이 4byte, double 배열이면 8byte

&val[2] (int *, 값 x+8) : 2번 원소의 주소

*(val+1) (int, 값 7) : 주소를 계산한 뒤 역참조 → val[1]의 값

val+i (int *, 값 x+4*i) : 일반형, 주소 = 시작 주소 + 원소 크기 × index

  • (보충) val[i]는 *(val+i)와 같은 뜻

zip_vec 예제

#define ZLEN 5
typedef int zip_vec[ZLEN];
zip_vec postech = {3, 7, 6, 7, 3};

zip_vec postech는 int postech[5]와 같은 선언 (typedef로 "int 5개짜리 배열"이라는 type 이름을 만든 것)

슬라이드 가정 : postech의 시작 주소가 16, 원소 간격 4 → 주소 16, 20, 24, 28, 32

zincr는 모든 원소를 1씩 증가시키는 함수 → 새 zip code는 4 8 7 8 4

zincr Assembly(어셈블리)

# z in %rdi
    movl    $0, %eax              # %eax = i
    jmp     .L3
.L4:                              # loop:
    addl    $1, (%rdi,%rax,4)     # z[i]++
    addq    $1, %rax              # i++
.L3:                              # middle
    cmpq    $4, %rax              # compare i and 4
    jbe     .L4                   # if <=, goto loop
    rep; ret

z는 첫 번째 인자 → %rdi (배열의 첫 byte 주소), %eax가 반복 변수 i

  • (보충) 구조는 Day 6의 jump-to-middle : 처음에 조건 검사(.L3)로 점프하고, 참이면 .L4 body로 돌아옴

cmpq $4, %rax + jbe .L4 : i가 4 이하이면 loop를 계속, 아니면 함수 종료

  • ZLEN = 5라서 i < 5가 i ≤ 4로 컴파일됨 → "4까지만 돈다"
  • (보충) size_t는 unsigned라서 signed용 jle이 아니라 unsigned용 jbe

addl $1, (%rdi,%rax,4) : 주소 의 메모리 값에 1을 더해 그 자리에 되써 넣음 → z[i]++

  • %rdi는 base(배열의 시작), %rax는 index, 4는 원소 크기(scale)
  • 컴파일러가 type이 int임을 알기 때문에 scale을 4로 정함

addq $1, %rax : i++

중첩(다차원) Array(배열)

2차원 Array(배열) 선언과 row-major 배치

배열은 1차원뿐 아니라 2차원, 다차원도 똑같이 간단 : 결국 "특정 위치로 점프"하는 주소 계산 → 2차원은 주소 계산이 두 번(행 위치, 열 위치) 필요하다고 상상하면 됨

T N[R][C]; : data type T, R개 행(row), C개 열(column)인 2차원 배열

  • 첫 번째 index가 행, 두 번째 index가 열

원소 개수 , 원소 하나가 k = sizeof(T) byte → 전체 크기 byte (int면 )

메모리는 byte의 1차원 배열(0부터 최대 주소까지 flat한 주소) → 2차원 행렬은 가상의 표현이고, 실제로는 일렬로 펴서(flatten) 저장해야 함

펴는 방법은 두 가지

  • row-major ordering : 가장 널리 쓰이는 방식 → 첫 행의 열 원소들을 연속으로, 그다음 둘째 행, 셋째 행 … 순서
  • column-major ordering : 첫 열의 행 원소들을 연속으로, 그다음 둘째 열 … 순서
  • (보충) 2×3 예 : row-major는 A00 A01 A02 A10 A11 A12, column-major는 A00 A10 A01 A11 A02 A12

왜 신경 쓰나 : cache (CPU 안의 작고 빠른 영역, 자주 접근한 데이터를 둠)와 관련

  • 행 방향으로 훑는지 열 방향으로 훑는지에 따라 접근이 연속적인지 건너뛰는지가 달라지고, cache 효율이 크게 달라짐
  • 학기 후반 cache 파트에서 다룰 예정 → 오늘은 row-major만 사용, 슬라이드도 중첩 배열은 row-major 배치가 보장된다고 함

행(row) 시작 주소

N[i] : C개 원소를 가진 배열이고 첫 원소 &N[i][0]를 가리킴 = i번째 행의 시작 주소

한 행의 크기 = byte (열 개수 × 원소 크기)

행 시작 주소

  • N은 2차원 배열 전체의 시작 주소, i = 0이면 N 자체
  • (보충) sizeof(N[i])가 곧 한 행의 크기 C * k

슬라이드 그림 (int A[R][C]) : A[0]은 A, A[i]는 A+i*(C*4), A[R-1]은 A+(R-1)*(C*4)

원소 주소

먼저 i번째 행의 시작 주소로 이동하고, 거기서 열 offset만큼 더 이동하면 원소 하나에 도달

N[i][j]는 type T, k byte짜리 원소

원소 주소

  • 앞 항 : 행 시작 주소 (행 하나의 크기 × 행 번호 i)
  • 뒤 항 : 행 안의 열 offset (j = 열 index, k = 원소 크기)
  • (보충) 오른쪽 식은 1차원으로 편 index 에 원소 크기 k를 곱한 꼴

슬라이드 그림 (int) : A[i][j]의 주소 = A+i*(C*4)+(j*4)

중첩 Array(배열) 예제 : pohang

#define PCOUNT 4
zip_vec pohang[PCOUNT] = {{3, 7, 6, 7, 0},
                          {3, 7, 6, 7, 1},
                          {3, 7, 6, 7, 3},
                          {3, 7, 6, 7, 4}};

zip_vec pohang[4]는 int pohang[4][5]와 같은 선언

  • 변수 pohang : 원소 4개짜리 배열이 연속으로 할당됨
  • 각 원소 : int 5개짜리 배열(앞에서 정의한 zip_vec)이 연속으로 할당됨
  • 전체 원소가 row-major 순서로 놓이는 것이 보장됨

슬라이드 그림 : pohang의 시작 주소 76, 행 시작 주소 76 / 96 / 116 / 136 → 행 하나가 20byte

  • flat하게 나열하면 20개 : 3 7 6 7 0 / 3 7 6 7 1 / 3 7 6 7 3 / 3 7 6 7 4

행 접근 코드 : get_pohang_zip

int *get_pohang_zip(int index) {
    return pohang[index];
}
# index in %rdi
leaq (%rdi,%rdi,4), %rax      # 5 * index
leaq pohang(,%rax,4), %rax    # pohang + (20*index)
ret

pohang[index]는 int 5개짜리 배열 → 반환하는 것은 그 행의 시작 주소

행 시작 주소 (슬라이드의 pohoang은 pohang 오타)

첫 leaq (%rdi,%rdi,4) : %rdi + 4·%rdi = 5 * index

  • 행 하나가 int 5개(열 개수 5)라서 5를 곱해야 함 → 곱셈 대신 lea 한 번으로 계산하는 "최적화된" 방식
  • (보충) scale에는 1, 2, 4, 8만 쓸 수 있어서 5배는 index + 4*index로 만듦

둘째 leaq pohang(,%rax,4) : base 없이 displacement = pohang(배열 label), index = %rax(= 5·index), scale 4(int 크기)

  • 둘 다 leaq라서 메모리를 읽지 않고 주소만 계산해서 반환

손계산 3 : pohang 행 시작 주소

행 하나 5 × 4 = 20 byte, 전체 4 × 20 = 80 byte → 주소 76 – 155 (다음 주소 156)

  • 그 행의 값은 3 7 6 7 4, 주소 136 – 155

행 시작 주소끼리의 간격은 늘 20 : 96 − 76 = 20, 116 − 96 = 20, 136 − 116 = 20

원소 접근 코드 : get_pohang_digit

int get_pohang_digit(int index, int col) {
    return pohang[index][col];
}

(보충) 슬라이드는 반환형이 int *로 적혀 있지만 원소 값을 반환하므로 int

# index in %rdi, col in %rsi
leaq  (%rdi,%rdi,4), %rax       # 5*index
addl  %rax, %rsi                # 5*index+col
movl  pohang(,%rsi,4), %eax     # M[pohang+4*(5*index+col)]
ret

(보충) 슬라이드는 addl로 적혀 있지만 64bit register끼리의 덧셈이라 실제로는 addq

주소

동작 순서

  • ① 첫 leaq로 행 위치 5*index
  • ② col을 더해 "1차원으로 폈을 때의 index" 5*index + col
  • ③ movl pohang(,%rsi,4)에서 원소 크기 4를 곱한 주소의 메모리를 읽어 %eax(반환값)에 저장

교수님 설명 : 먼저 목표 행으로 이동한 뒤 목표 열만큼 조금 더 이동하는 두 단계 → 코드는 이 둘을 index 하나와 scale 4로 합쳐서 처리

  • 이번에는 movl이라 메모리를 실제로 읽음 (앞의 leaq는 주소만 계산)

손계산 4 : pohang[2][3] 읽기

get_pohang_digit(2, 3) : %rdi = 2, %rsi = 3, pohang = 76

leaq (%rdi,%rdi,4), %rax      %rax = 2 + 4*2 = 10
addl %rax, %rsi               %rsi = 3 + 10  = 13
movl pohang(,%rsi,4), %eax    주소 = 76 + 4*13 = 76 + 52 = 128  →  %eax = M[128]

검산 : 행 2의 시작 116 + 열 3 × 4 = 116 + 12 = 128 → 같은 주소

  • 식으로도

값 : 20개를 flat하게 나열하면 index 10 – 14가 3 7 6 7 3 → index 13은 7 → %eax = 7 (슬라이드 그림에서 파란 행의 네 번째 칸)

다른 칸도 같은 식으로

  • pohang[0][0] → 76 + 0 + 0 = 76, 값 3
  • pohang[1][4] → 76 + 20 + 16 = 112, 값 1
  • pohang[3][4] → 76 + 60 + 16 = 152, 값 4 → 마지막 원소, 152 + 4 = 156 = 76 + 80 (배열 끝 다음 주소)

변수 univ는 포인터(8byte) 원소 3개짜리 배열 → 각 포인터가 int 5개짜리 배열을 가리킴 (슬라이드 14)

  • 앞의 nested 배열 pohang은 5개짜리 행 4개가 한 덩어리로 붙어 있었음
  • 여기서는 행 3개가 따로 선언되어 있고, univ는 그 행들의 시작 주소만 모아 둔 배열

슬라이드 가정 : univ의 시작 주소 160 → 칸 주소는 160, 168, 176 (원소 간격 8byte)

  • univ[0] = 16 → postech (주소 16 – 35)
  • univ[1] = 56 → kaist (주소 56 – 75) : 초기화 순서가 {postech, kaist, snu}라서 둘째 칸이 kaist
  • univ[2] = 36 → snu (주소 36 – 55)

행 시작 주소가 16, 56, 36으로 규칙 없이 흩어져 있음 → nested 배열의 행 시작이 늘 로 간격이 일정했던 것과 다른 점

  • (보충) 포인터만 저장하므로 각 행이 메모리 어디에 있어도 되고 행마다 길이가 달라도 됨. 대신 원소를 읽을 때 포인터를 한 번 따라가야 함

원소 접근 코드 : get_univ_digit

int get_univ_digit(size_t index, size_t col) {
    return univ[index][col];
}
# index in %rdi, col in %rsi
salq    $2, %rsi              # 4*dig
addq    univ(,%rdi,8), %rsi   # p = univ[index] + 4*dig
movl    (%rsi), %eax          # return *p
ret

슬라이드는 열 index col을 주석에서 dig(digit)라고 부름

salq $2, %rsi : col을 왼쪽으로 2칸 shift → 4*col, 원소(int) 크기 4를 곱한 열 offset

addq univ(,%rdi,8), %rsi : 메모리 univ + 8*index에서 행 포인터 univ[index]를 읽어 열 offset에 더함 → p

  • scale 8은 포인터 크기 (univ의 원소가 포인터라서)
  • (보충) 이 한 명령이 메모리 읽기(첫 번째)와 덧셈을 함께 함

movl (%rsi), %eax : p가 가리키는 int를 읽어 반환값으로 (두 번째 메모리 읽기)

슬라이드 정리 : 접근 식은 Mem[Mem[univ+8*index]+4*dig] → 메모리 읽기가 두 번

  • 첫 번째는 목표 행 배열의 포인터를 얻기 위해, 두 번째는 그 배열 안의 목표 원소에 접근하기 위해

손계산 5 : nested와 multi-level 원소 접근 비교 (index = 1, col = 2)

nested : pohang[1][2]    (pohang = 76, 행 하나 20byte)
  주소 = 76 + 20*1 + 4*2 = 104
  메모리 읽기 1번 : M[104] = 6        (행 1 = 3 7 6 7 1의 셋째 값)

multi-level : get_univ_digit(1, 2)    (univ = 160, %rdi = 1, %rsi = 2)
  salq $2, %rsi                %rsi = 2 * 4 = 8
  addq univ(,%rdi,8), %rsi     160 + 8*1 = 168 → M[168] = 56      (첫 번째 읽기)
                               %rsi = 8 + 56 = 64
  movl (%rsi), %eax            M[64] = 1                          (두 번째 읽기, kaist의 셋째 값)

univ[2][4]도 같은 순서 : M[160 + 8*2] = M[176] = 36 → 36 + 4*4 = 52 → M[52] = 0 (snu의 마지막 값)

같은 열 offset 8(= col 2)이어도 행 포인터가 달라서 도착하는 곳이 달라짐

  • univ[0] → 16 + 8 = 24 (값 6), univ[1] → 56 + 8 = 64 (값 1), univ[2] → 36 + 8 = 44 (값 8)

정리 : nested는 주소를 산술로만 구해 읽기 1번, multi-level은 행 포인터를 읽고 원소를 읽어 2번

N×N 행렬

이 부분은 수업 녹화가 없어 슬라이드만 보고 정리함

행렬 코드의 세 가지 형태

같은 a[i][j] 읽기를 세 가지 방식으로 보여 줌 (슬라이드 16)

Fixed dimensions : 컴파일 시점에 N을 앎

#define N 16
typedef int fix_matrix[N][N];
/* Get element a[i][j] */
int fix_ele(fix_matrix a, int i, int j) {
    return a[i][j];
}

Variable dimensions, explicit indexing : 동적 배열을 구현하는 전통적인 방법 → 1차원 배열로 받고 index를 직접 계산

#define IDX(n, i, j) ((i)*(n)+(j))
/* Get element a[i][j] */
int vec_ele(size_t n, int *a, int i, int j) {
    return a[IDX(n,i,j)];
}

Variable dimensions, implicit indexing : 지금은 gcc가 지원

/* Get element a[i][j] */
int var_ele(size_t n, int a[n][n], int i, int j) {
    return a[i][j];
}

(보충) 세 번째는 i*n+j 계산을 컴파일러가 해 주므로 소스에는 a[i][j]를 그대로 씀. 인자 n이 a보다 앞에 와야 a[n][n]에서 쓸 수 있음

16×16 행렬 접근

원소 주소 에서 C = n, k = 4 (슬라이드 17)

  • (보충) 이 예에서는 열 개수가 16, int라서 k = 4 → 한 행 16 × 4 = 64 byte
# a in %rdi, i in %rsi, j in %rdx
salq    $6, %rsi              # 64*i
addq    %rsi, %rdi            # a + 64*i
movl    (%rdi,%rdx,4), %eax   # M[a + 64*i + 4*j]
ret

salq $6, %rsi : 왼쪽으로 6칸 shift = 64배 → 행 시작까지의 offset 64*i

  • 행 하나가 64 = byte라서 곱셈 없이 shift로 계산

addq %rsi, %rdi : a + 64*i = i번째 행의 시작 주소

movl (%rdi,%rdx,4), %eax : base = 행 시작, index = j, scale = 4 → a + 64*i + 4*j의 값을 읽음

N이 컴파일 시점의 상수라서 행 크기도 상수 → shift와 덧셈만으로 주소가 나옴

n×n 행렬 접근

같은 식에서 C = n, k = 4인데 n이 실행 중에 정해짐 → 슬라이드 : 정수 곱셈을 해야 함 (슬라이드 18)

# n in %rdi, a in %rsi, i in %rdx, j in %rcx
imulq   %rdx, %rdi             # n*i
leaq    (%rsi,%rdi,4), %rax    # a + 4*n*i
movl    (%rax,%rcx,4), %eax    # a + 4*n*i + 4*j
ret

imulq %rdx, %rdi : %rdi = n * i (행 번호 × 열 개수)

leaq (%rsi,%rdi,4), %rax : a + 4*(n*i) = 행 시작 주소, scale 4가 원소 크기

movl (%rax,%rcx,4), %eax : 열 offset 4*j를 더해서 읽음

16×16과 비교 : 행 크기 64가 상수일 때는 salq $6, 행 크기 4*n이 변수일 때는 imulq

손계산 6 : 16×16과 n×n의 원소 주소 (a = 0x1000, i = 3, j = 5)

fix_ele(a, 3, 5)
  salq $6, %rsi              %rsi = 3 << 6 = 192
  addq %rsi, %rdi            %rdi = 0x1000 + 192 = 0x10C0
  movl (%rdi,%rdx,4), %eax   주소 = 0x10C0 + 4*5 = 0x10C0 + 20 = 0x10D4

var_ele(16, a, 3, 5)
  imulq %rdx, %rdi           %rdi = 16 * 3 = 48
  leaq (%rsi,%rdi,4), %rax   %rax = 0x1000 + 4*48 = 0x1000 + 192 = 0x10C0
  movl (%rax,%rcx,4), %eax   주소 = 0x10C0 + 4*5 = 0x10D4

검산 : (3 × 16 + 5) × 4 = 212 = 0xD4 → 0x1000 + 0xD4 = 0x10D4, 두 함수가 같은 주소를 읽음

n = 10이면 : imulq로 10 × 3 = 30, leaq → 0x1000 + 4 × 30 = 0x1078, 열 offset 4 × 5 = 20을 더해 0x108C

  • 검산 : (3 × 10 + 5) × 4 = 140 = 0x8C → 0x1000 + 0x8C = 0x108C

Struct(구조체) 표현과 멤버 접근

이 부분은 수업 녹화가 없어 슬라이드만 보고 정리함

struct 표현

struct rec {
    int a[4];
    size_t i;
    struct rec *next;
};

구조체는 모든 field를 담을 만큼 큰 메모리 block 하나로 표현됨 (슬라이드 20)

field는 선언한 순서대로 배치됨 → 다른 순서가 더 compact한 표현을 만들 수 있어도 순서를 바꾸지 않음

전체 크기와 field 위치는 컴파일러가 정함 → 기계어 수준 프로그램은 소스의 구조체를 이해하지 못함 (남는 것은 offset 숫자뿐)

슬라이드 그림 : a는 0부터, i는 16부터, next는 24부터 시작해 31에서 끝남 (눈금 0, 16, 24, 31)

  • next는 다음 struct rec의 시작 r을 가리키는 포인터 (그림의 화살표)
  • (보충) 크기 : a 4 × 4 = 16, i(size_t) 8, next(포인터) 8 → 16 + 8 + 8 = 32 byte

멤버 Pointer(포인터) 생성 : get_ap

배열 member의 원소 주소를 만드는 경우 : 각 member의 offset은 컴파일 시점에 결정됨 → 주소는 r+4*idx로 계산 (a의 offset이 0) (슬라이드 21)

int *get_ap(struct rec *r, size_t idx) {
    return &r->a[idx];
}
# r in %rdi, idx in %rsi
leaq (%rdi,%rsi,4), %rax
ret

leaq 하나 : base = r, index = idx, scale = 4(int 크기) → 메모리를 읽지 않고 주소만 계산해 반환

set_val : next를 따라가며 a[i]에 쓰기

void set_val(struct rec *r, int val) {
    while (r) {
        int i = r->i;
        r->a[i] = val;
        r = r->next;
    }
}
.L11:                                   # loop:
    movslq  16(%rdi), %rax              #   i = Mem[r+16]
    movl    %esi, (%rdi,%rax,4)         #   Mem[r+4*i] = val
    movq    24(%rdi), %rdi              #   r = Mem[r+24]
    testq   %rdi, %rdi                  #   Test r
    jne     .L11                        #   if !=0 goto loop

레지스터 : %rdi = r, %rsi = val (슬라이드 22)

member 접근이 전부 r에 offset을 더하는 꼴 : 16(%rdi) = r->i(offset 16), 24(%rdi) = r->next(offset 24), (%rdi,%rax,4) = r->a[i](offset 0 + 4*i)

  • (보충) r->i는 8byte size_t인데 int i에 담으므로 아래쪽 4byte만 movslq로 읽어 64bit로 부호 확장

testq %rdi, %rdi + jne .L11 : r이 0이 아니면 다음 node로 loop를 계속, 0이면 종료

  • 슬라이드에는 loop 몸체만 나옴

Struct(구조체) Alignment(정렬)(alignment)

이 부분은 수업 녹화가 없어 슬라이드만 보고 정리함

Alignment(정렬) 안 된 데이터와 정렬된 데이터

struct S1 {
    char c;
    int i[2];
    double v;
} *p;

Unaligned data : 멤버를 빈틈없이 붙인 배치 (슬라이드 23)

  • c는 p, i[0]은 p+1, i[1]은 p+5, v는 p+9, 끝은 p+16 → 17byte

Aligned data : 기본 data type이 B byte를 요구하면 주소가 B의 배수여야 함

  • c는 p+0, i[0]은 p+4(4의 배수), i[1]은 p+8, v는 p+16(8의 배수), 끝은 p+23 → 24byte
  • 그림의 회색 칸이 빈틈(padding) : p+1 – p+3(3byte)와 p+12 – p+15(4byte)
  • (보충) 그림의 p+0 아래 "Multiple of 8"는 c(1byte)가 아니라 구조체 시작 주소 p가 8의 배수여야 한다는 뜻으로 읽음 (아래 K 설명)

Alignment(정렬) 원칙

슬라이드 24는 글만 있음

Aligned data : 기본 data type이 B byte를 요구하면 주소는 B의 배수

  • 일부 machine에서는 필수, x86-64에서는 권장 (advised)

정렬하는 동기

  • memory는 (시스템에 따라) 4byte 또는 8byte 단위의 정렬된 chunk로 접근됨
  • quad-word 경계에 걸친 data를 load/store하는 것은 비효율
  • virtual memory : data가 두 page에 걸치면 더 까다로움

compiler가 구조체 안에 gap(padding)을 넣어서 각 field의 정렬을 맞춤

  • (보충) 요구하는 B는 type 크기와 같음 : char 1, short 2, int와 float 4, long, double, 포인터 8

Struct(구조체) 안과 전체의 Alignment(정렬) 맞추기

구조체 안 : 각 element의 정렬 요구를 만족해야 함 (슬라이드 25)

구조체 전체 배치 : 구조체마다 정렬 요구 K가 있음

  • K = element들 중 가장 큰 정렬 요구
  • 구조체의 시작 주소와 구조체 길이가 모두 K의 배수여야 함

예 : S1은 double element 때문에 K = 8

그림 : c가 p+0, 회색 internal padding, i[0]이 p+4(4의 배수), i[1]이 p+8, 두 번째 internal padding, v가 p+16(8의 배수), 끝이 p+23

  • padding 두 군데가 모두 구조체 안쪽이라서 internal padding이라고 부름

Struct(구조체) 전체 길이를 K의 배수로

struct S2 {
    double v;
    int i[2];
    char c;
} *p;

가장 큰 정렬 요구가 K이면 구조체 전체 길이가 K의 배수여야 함 (슬라이드 26)

S2의 그림 : v가 p+0, i[0]이 p+8, i[1]이 p+12, c가 p+16, 그 뒤 회색 칸이 끝(p+23)까지 이어짐 → 전체 24byte, 8의 배수

  • 슬라이드 오른쪽의 희미한 상자는 앞의 S1 (멤버는 같고 순서만 다름)
  • (보충) c 뒤에서 끝내면 17byte라서 8의 배수가 아니므로 뒤쪽에 7byte를 채움 (trailing padding)

Struct(구조체) Array(배열)

struct S2 {

    int i[2];
    char c;

a[0]은 a, a[1]은 a+24, a[2]는 a+48 → 원소 하나가 24byte

  • (보충) 끝 padding이 없으면 원소 크기가 17이 되어 a[1]의 v가 a+17에 놓여 8의 배수가 아님

그림 : a[idx]는 a+12*idx에서 a+12*idx+11까지, 안쪽은 i / 회색 / v / j / 회색

leaq (%rdi,%rdi,2), %rax : idx + 2*idx = 3*idx

  • (보충) 12배는 scale에 쓸 수 없어서(1, 2, 4, 8뿐) 3배를 먼저 만들고 movzwl의 scale 4로 12*idx를 완성

movzwl a+8(,%rax,4), %eax : 주소 a + 8 + 4*(3*idx) = a + 12*idx + 8에서 short 2byte를 읽어 0으로 채워 %eax에 넣음

  • (보충) movz 계열은 zero extend, w는 2byte(word) 원본, l은 4byte 목적지

  • 같은 멤버인데 순서만 바꿔 padding이 6byte에서 2byte로 줄어듦

배경 : x87, SSE, AVX

  • SIMD = Single Instruction Multiple Data : 명령어 하나로 여러 data를 한꺼번에 처리
  • 오래된 machine이 지원
  • vector instruction의 특수한 경우로 사용

XMM register

XMM register는 16개, 각각 16byte (슬라이드 32)

같은 16byte를 해석하는 방법이 여러 가지

  • 정수 : 1byte 정수 16개, 16bit 정수 8개, 32bit 정수 4개
  • 부동소수점 : single-precision float 4개, double-precision float 2개
  • 맨 아래 두 줄 : single-precision 1개(낮은 4byte만), double-precision 1개(낮은 8byte만) → scalar 연산이 쓰는 부분

(보충) 칸 수 × 크기가 모두 16byte : 16 × 1, 8 × 2, 4 × 4, 4 × 4(float), 2 × 8(double)

scalar와 SIMD 연산

세 가지 덧셈 (슬라이드 33)

  • addss %xmm0,%xmm1 : scalar, single precision → 낮은 4byte 한 쌍만 더함
  • addps %xmm0,%xmm1 : SIMD, single precision → float 4개를 칸끼리 동시에 더함
  • addsd %xmm0,%xmm1 : scalar, double precision → 낮은 8byte 한 쌍만 더함

그림 : 더하기 표시가 xmm0과 xmm1의 같은 위치 칸 사이에 있고, 결과 화살표는 xmm1 쪽으로 향함

  • scalar는 더하기 표시가 한 개(낮은 칸), SIMD는 네 개

(보충) 이름 규칙 : 앞 add는 덧셈, 가운데 s는 scalar / p는 packed(SIMD), 끝 s는 single / d는 double

(보충) AT&T 순서라서 결과는 두 번째 인자 %xmm1에 저장됨

FP 기본 : 인자와 반환

FP 값은 XMM register로 전달됨 (슬라이드 34)

  • 인자는 %xmm0, %xmm1, ... 순서
  • 반환값은 %xmm0
  • XMM register는 모두 caller-saved
    • (보충) callee-saved인 XMM register가 하나도 없으므로, 호출 뒤에도 값이 필요하면 호출하는 쪽이 미리 저장해야 함
float fadd(float x, float y) {
    return x + y;
}
# x in %xmm0, y in %xmm1
addss   %xmm1, %xmm0
ret
double dadd(double x, double y) {
    return x + y;
}
# x in %xmm0, y in %xmm1
addsd   %xmm1, %xmm0
ret

addss %xmm1, %xmm0은 %xmm0 = %xmm0 + %xmm1이라 결과가 곧바로 반환 register %xmm0에 들어 있음 → 따로 옮기는 명령이 없음

dadd는 같은 구조에서 single(ss) 대신 double(sd) 명령을 씀

FP 메모리 참조 : dincr

정수와 포인터 인자는 일반 register, FP 값은 XMM register로 전달 (슬라이드 35)

  • XMM register끼리 옮기는 mov와 memory ↔ XMM register 사이를 옮기는 mov가 서로 다른 명령어
double dincr(double *p, double v) {
    double x = *p;
    *p = x + v;
    return x;
}
# p in %rdi, v in %xmm0
movapd  %xmm0, %xmm1       # Copy v
movsd   (%rdi), %xmm0      # x = *p
addsd   %xmm0, %xmm1       # t = x + v
movsd   %xmm1, (%rdi)      # *p = t
ret

p는 포인터라서 %rdi, v는 double이라서 %xmm0

movapd %xmm0, %xmm1 : XMM끼리 복사 → v를 %xmm1에 보관

movsd (%rdi), %xmm0 : memory → XMM, x = *p

addsd %xmm0, %xmm1 : t = x + v는 %xmm1에

movsd %xmm1, (%rdi) : XMM → memory, *p = t

ret : x가 %xmm0에 있어서 return x를 위한 명령이 따로 없음

  • (보충) 처음에 v를 %xmm1로 복사하는 이유 : 다음 movsd가 %xmm0을 덮어써서 v가 사라지기 때문

손계산 11 : scalar와 SIMD 덧셈, dincr 추적

float 4칸 (왼쪽이 낮은 칸), 초기값
  %xmm0 = [1.0, 2.0, 3.0, 4.0]
  %xmm1 = [10.0, 20.0, 30.0, 40.0]
addss %xmm0,%xmm1 → %xmm1 = [11.0, 20.0, 30.0, 40.0]     (낮은 칸 한 쌍만 : 10.0 + 1.0)
addps %xmm0,%xmm1 → %xmm1 = [11.0, 22.0, 33.0, 44.0]     (네 칸 모두)

double 2칸, 초기값
  %xmm0 = [1.5, 9.0]
  %xmm1 = [2.0, 7.0]
addsd %xmm0,%xmm1 → %xmm1 = [3.5, 7.0]                   (낮은 8byte만 : 2.0 + 1.5, 위쪽 칸은 그대로)

위 두 블록은 각각 초기값에서 따로 실행한 결과 (addss와 addps를 이어서 실행한 것이 아님)

dincr 추적 : *p = 1.5, v = 2.0

시작                     %xmm0 = v = 2.0,  M[p] = 1.5
movapd %xmm0, %xmm1      %xmm1 = 2.0
movsd (%rdi), %xmm0      %xmm0 = 1.5                (x)
addsd %xmm0, %xmm1       %xmm1 = 2.0 + 1.5 = 3.5    (t)
movsd %xmm1, (%rdi)      M[p] = 3.5
ret                      반환값 %xmm0 = 1.5          (옛 *p)

결과 : *p는 1.5 → 3.5로 바뀌고, 반환값은 바뀌기 전 값 1.5

시험 포인트

T N[L]은 연속된 L * sizeof(T) byte, 원소 i의 주소 = 시작 주소 + sizeof(T) * i (char 1, short 2, int 4, long/포인터/double 8)

배열 이름은 첫 원소의 주소 : val, val+1, &val[2], val+i는 int *이고 값은 x, x+4, x+8, x+4*i → 포인터에 더하는 정수는 원소 크기만큼 곱해짐

*(val+1)은 val[1]의 값, 범위 밖 val[5]의 값은 알 수 없음

Intel은 little endian : int 3은 03 00 00 00으로 저장

addl $1, (%rdi,%rax,4) = z[i]++ : base = 배열 시작, index = i, scale = 원소 크기, 메모리 값을 직접 갱신

for (i = 0; i < 5; i++)는 cmpq $4, %rax + jbe로 컴파일됨 (size_t는 unsigned 비교)

T N[R][C] : 크기 R*C*k, row-major 배치, 한 행은 C*k byte

행 시작 주소 = N + i*(C*k), 원소 주소 = N + i*(C*k) + j*k = N + (i*C + j)*k

pohang[4][5] (int) : 행 크기 20, 원소 주소 = pohang + 20*index + 4*col

leaq (%rdi,%rdi,4) = 5*index (scale은 1, 2, 4, 8뿐이라 x + 4x로 5배), 이어지는 leaq pohang(,%rax,4) 또는 movl pohang(,%rsi,4)가 원소 크기 4를 곱함

row-major와 column-major 중 어느 쪽으로 훑느냐가 cache 효율에 영향 (cache는 뒤에서 다룸)

int *univ[3] 같은 multi-level 배열은 원소 접근에 메모리 읽기가 두 번 : Mem[Mem[univ+8*index]+4*dig] (행 포인터를 읽고, 그 행에서 원소를 읽음), nested 배열은 주소를 계산해 한 번만 읽음

multi-level 배열의 행은 포인터가 가리키는 곳이라 서로 떨어져 있을 수 있음 (슬라이드 예 : 16, 56, 36), nested 배열은 행 간격이 항상 C*k

고정 크기 int [16][16] 접근은 salq $6, %rsi(64*i) + addq + movl (%rdi,%rdx,4), 변수 크기 a[n][n]은 imulq로 n*i를 구한 뒤 leaq (%rsi,%rdi,4) + movl (%rax,%rcx,4) → 주소는 둘 다 a + 4*n*i + 4*j (행 크기가 상수여야 곱셈을 shift로 바꿀 수 있음)

구조체 field는 선언 순서대로 놓이고 offset은 컴파일 시점에 정해짐 : struct rec {int a[4]; size_t i; struct rec *next;}는 offset 0 / 16 / 24, 크기 32, &r->a[idx]는 leaq (%rdi,%rsi,4), %rax 한 줄

정렬 : 기본 type이 B byte를 요구하면 주소는 B의 배수, 구조체는 K = field 중 가장 큰 정렬 요구, 시작 주소와 전체 길이가 K의 배수가 되도록 compiler가 internal padding과 끝 padding을 넣음

struct S1 {char c; int i[2]; double v;} : offset 0, 4, 16, sizeof 24 (padding 3 + 4) / 순서를 바꾼 struct S2 {double v; int i[2]; char c;} : offset 0, 8, 16, 끝 padding 7 → 크기는 똑같이 24

구조체 배열 원소 a[idx]의 주소 = a + sizeof*idx (padding 포함 크기), member는 거기에 offset을 더함 : struct S3 {short i; float v; short j;}는 sizeof 12, j의 offset 8 → leaq (%rdi,%rdi,2), %rax(3*idx) + movzwl a+8(,%rax,4), %eax

공간 절약은 큰 type을 앞에 : struct S4 {char c; int i; char d;} 12byte → struct S5 {int i; char c; char d;} 8byte

FP : XMM register는 16개, 각 16byte, 인자는 %xmm0, %xmm1, ... 반환은 %xmm0, 전부 caller-saved / addss, addsd는 scalar(낮은 4 / 8byte 한 쌍), addps는 SIMD(float 4개 동시)

FP 값은 XMM register, 정수와 포인터 인자는 일반 register(dincr는 p가 %rdi, v가 %xmm0) / 이동 명령어가 다름 : XMM끼리는 movapd, memory ↔ XMM은 movsd

# n in %rdi, a in %rsi, i in %rdx, j in %rcx
imulq   %rdx, %rdi              # (a)
leaq    (%rsi,%rdi,__), %rax    # (b)
movq    (%rax,%rcx,__), %rax    # (c)
ret
답

(a) n*i (b) scale 8, a + 8*n*i (c) scale 8, a + 8*n*i + 8*j (long이라 원소 크기 8)

n*i = 7 × 4 = 28 → 0x3000 + 8 × 28 = 0x3000 + 224 = 0x30E0 → 열 offset 8 × 2 = 16을 더해 0x30F0

검산 : (4 × 7 + 2) × 8 = 240 = 0xF0 → 0x3000 + 0xF0 = 0x30F0

fix[8][8]은 행 하나가 8 × 8 = 64byte = → 곱셈 대신 salq $6, %rsi (64*i)

문제 10

struct T { short s; char c; double d; int i; };에서 (1) 각 member의 offset과 sizeof, (2) padding 총량, (3) member 순서를 d, i, s, c로 바꾼 구조체의 offset과 sizeof, 줄어든 크기를 구하라.

답

(1) K = 8(double). s 0 (끝 2), c 2 (끝 3), d는 3을 8의 배수로 올려 8 (끝 16), i 16 (끝 20), 전체 20을 8의 배수로 올려 sizeof = 24

(2) member 크기 2 + 1 + 8 + 4 = 15 → padding 24 − 15 = 9byte (3 – 7, 20 – 23)

(3) d 0 (끝 8), i 8 (끝 12), s 12 (끝 14), c 14 (끝 15), 전체 15를 8의 배수로 올려 sizeof = 16 → 24 − 16 = 8byte 감소 (padding 1byte뿐)

문제 11

struct P { char tag; double val; short n; } arr[20];가 있고 arr의 시작 주소는 0x5000이다. (1) sizeof(struct P)와 arr 전체 크기, (2) &arr[7].n, (3) short get_n(int idx) { return arr[idx].n; }가 아래처럼 컴파일되었을 때 빈칸 두 개와 %rax의 값(idx = 7)을 구하라.

# idx in %rdi
leaq    (%rdi,%rdi,2), %rax
movzwl  arr+__(,%rax,__), %eax
ret
답

(1) K = 8. tag 0, val 8, n 16(끝 18) → 18을 8의 배수로 올려 sizeof = 24, 전체 24 × 20 = 480 = 0x1E0 byte

(2) 0x5000 + 24 × 7 + 16 = 0x5000 + 168 + 16 = 0x5000 + 184 = 0x50B8

(3) n의 offset이 16이므로 첫 빈칸 16, %rax = 3*idx에 곱해 24*idx가 되려면 scale 8 → arr+16(,%rax,8)

idx = 7이면 %rax = 7 + 2 × 7 = 21, 주소 0x5000 + 16 + 8 × 21 = 0x5000 + 16 + 168 = 0x50B8

문제 12

(1) long f(long n, double x, float y, double *p)의 네 인자는 각각 어느 register로 전달되는가? (2) dincr가 *p = 3.25, v = 0.75에서 실행될 때 movapd, movsd (%rdi), %xmm0, addsd, movsd %xmm1, (%rdi) 직후의 값과 반환값을 구하라. (3) %xmm0 = [1.5, 2.5, 3.5, 4.5], %xmm1 = [0.5, 0.5, 0.5, 0.5](float 4칸)일 때 addps %xmm0,%xmm1과 addss %xmm0,%xmm1을 각각 실행한 뒤의 %xmm1은?

답

(1) 정수와 포인터는 일반 register 순서, FP는 XMM register 순서 : n → %rdi, p → %rsi, x → %xmm0, y → %xmm1

(2) movapd %xmm0, %xmm1 → %xmm1 = 0.75, movsd (%rdi), %xmm0 → %xmm0 = 3.25, addsd %xmm0, %xmm1 → %xmm1 = 0.75 + 3.25 = 4.0, movsd %xmm1, (%rdi) → M[p] = 4.0, 반환값 %xmm0 = 3.25 (옛 *p)

(3) addps : 네 칸 모두 더해 [2.0, 3.0, 4.0, 5.0]

addss : 낮은 칸만 1.5 + 0.5 = 2.0이 되고 나머지는 그대로 [2.0, 0.5, 0.5, 0.5]
