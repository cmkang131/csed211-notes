1데이터 파트의 시작

오늘의 범위: array 먼저, struct는 그다음

지금까지는 기본 data type을 하나씩만 다뤘음: char 1byte, short 2byte, int 4byte, long·포인터·double 8byte. 이제는 같은 종류의 값을 모아 저장하는 array와 서로 다른 type을 묶는 struct를 다룸.
  • 아키텍처가 하는 일은 최소한: 64bit register를 통째로, 절반, 1/4로 쓸 수 있어서 8·4·2·1 byte 기본 type을 표현할 수 있을 뿐
  • "int 배열"을 직접 표현하는 하드웨어 기능은 없음
  • 배열 접근은 전부 offset 계산: 앞에서 배운 lea의 주소 지정 모드(base, index, scale, displacement)로 특정 index의 주소를 계산
  • 컴파일러는 배열 인덱스를 base·index·scale·displacement를 이용한 주소 계산으로 변환한다. 그러나 일반적인 C에서는 배열 범위 검사를 자동으로 보장하지 않으므로, 유효한 인덱스를 사용하는 것은 프로그래머의 책임이다.
  • 결국 "base 주소가 어디이고 offset이 얼마인가"로 귀결 → 포인터/주소 산술로 1차원 배열, 다차원 배열, struct에 접근하는 방법을 배움
  • 슬라이드 2 agenda: Arrays (One-Dimensional → Multi-Dimensional(Nested) → Multi-Level) → Structures (Allocation, Access, Alignment) → Floating Point

3zincr: 배열을 도는 어셈블리

#define ZLEN 5
typedef int zip_vec[ZLEN];
zip_vec postech = {3, 7, 6, 7, 3};

void zincr(zip_vec z) {        // int z[5]와 같은 선언 (typedef로 만든 type 이름)
    size_t i;
    for (i = 0; i < ZLEN; i++)
        z[i]++;              // 모든 원소를 1씩 증가 → 새 zip code는 4 8 7 8 4
}
# z in %rdi
    movl $0, %eax            # %eax = i
    jmp .L3
.L4:                          # loop:
    addl $1, (%rdi,%rax,4)    # z[i]++
    addq $1, %rax             # i++
.L3:                          # middle
    cmpq $4, %rax             # compare i and 4
    jbe .L4                   # if <=, goto loop
    rep; ret
  • z는 첫 번째 인자 → %rdi (배열의 첫 byte 주소), %rax가 반복 변수 i
  • 구조는 Lec5의 jump-to-middle: 처음에 조건 검사(.L3)로 점프하고, 참이면 .L4 body로 돌아옴
  • cmpq $4, %rax + jbe: ZLEN = 5라서 i < 5가 i ≤ 4로 컴파일됨
  • size_t는 unsigned라 signed용 jle가 아니라 unsigned용 jbe
  • addl $1, (%rdi,%rax,4): 주소 의 메모리 값에 1을 더해 그 자리에 씀 → z[i]++
  • base = 배열 시작(%rdi), index = i(%rax), scale = 원소 크기(4). 컴파일러가 type이 int임을 알기 때문에 scale을 4로 정함

4중첩(다차원) 배열: row-major

  • T N[R][C]; : data type T, R개 행, C개 열. 첫 번째 index가 행, 두 번째 index가 열
  • 원소 개수 , 원소 하나가 byte → 전체 크기 byte (int면 )
  • 메모리는 byte의 1차원 배열 → 2차원 행렬은 가상의 표현이고 실제로는 일렬로 펴서 저장
  • 펴는 방법 두 가지. row-major가 가장 널리 쓰이고 이 수업에서 사용:
방식순서2×3 예
row-major ordering첫 행의 열 원소들을 연속으로, 그다음 둘째 행, …A00 A01 A02 A10 A11 A12
column-major ordering첫 열의 행 원소들을 연속으로, …A00 A10 A01 A11 A02 A12
  • 슬라이드도 중첩 배열은 row-major 배치가 보장된다고 함
행 의 시작 주소 = · 원소 의 주소 =

행 접근: get_pohang_zip

int *get_pohang_zip(int index) {
    return pohang[index];       // int 5개짜리 배열 → 그 행의 시작 주소를 반환
}
# index in %rdi
    leaq (%rdi,%rdi,4), %rax    # 5 * index
    leaq pohang(,%rax,4), %rax  # pohang + (20*index)
    ret
  • 행 시작 주소 = (슬라이드의 "pohoang"은 pohang 오타)
  • 첫 leaq (%rdi,%rdi,4): %rdi + 4·%rdi = 5 × index. 행 하나가 int 5개라 5를 곱함
  • scale에는 1, 2, 4, 8만 쓸 수 있어서 5배는 index + 4×index로 만듦 (곱셈 대신 lea 한 번)
  • 둘째 leaq pohang(,%rax,4): displacement = pohang(배열 label), index = %rax(= 5·index), scale 4(int 크기)
  • 둘 다 leaq라 메모리를 읽지 않고 주소만 계산해 반환
  • 검산 (pohang = 76): index 0→76, 1→76+20=96, 2→116, 3→136. get_pohang_zip(3): %rax = 15 → 76 + 60 = 136 → 마지막 행(3 7 6 7 4, 주소 136~155)의 시작

원소 접근: get_pohang_digit

int get_pohang_digit(int index, int col) {
    return pohang[index][col];  // 슬라이드는 반환형이 int *로 적혀 있으나 원소 값을 반환하므로 int
}
# index in %rdi, col in %rsi
    leaq (%rdi,%rdi,4), %rax    # 5*index
    addq %rax, %rsi             # 5*index+col  (슬라이드 표기 addl — index·col이 32bit int라 상위 32bit는 자동으로 0이 되어 addq와 결과 동일)
    movl pohang(,%rsi,4), %eax  # M[pohang+4*(5*index+col)]
    ret
  • 주소 =
  • 첫 leaq로 행 위치 5·index
  • col을 더해 "1차원으로 폈을 때의 index" 5·index + col
  • movl에서 원소 크기 4를 곱한 주소의 메모리를 읽어 %eax에 저장. 이번에는 movl이라 메모리를 실제로 읽음

손계산: get_pohang_digit(2, 3) (pohang = 76)

  1. leaq (%rdi,%rdi,4), %rax → %rax = 2 + 4·2 = 10
  2. addq %rax, %rsi → %rsi = 3 + 10 = 13 (슬라이드 표기 addl — index·col이 32bit int라 5·index+col이 32bit 범위를 넘지 않는 이 예에서는 addq와 결과 동일; 32bit 쓰기는 상위 32bit를 0으로 만듦)
  3. movl pohang(,%rsi,4), %eax → 주소 = 76 + 4·13 = 76 + 52 = 128 → %eax = M[128]
  4. 검산: 행 2의 시작 116 + 열 3 × 4 = 116 + 12 = 128 → 같은 주소. 식으로도
  5. flat하게 나열한 20개에서 index 10~14가 3 7 6 7 3 → index 13은 7 → %eax = 7 (슬라이드 그림에서 파란 행의 네 번째 칸)
다른 칸도 같은 식: pohang[0][0] → 76 (값 3) · pohang[1][4] → 76 + 20 + 16 = 112 (값 1) · pohang[3][4] → 76 + 60 + 16 = 152 (값 4) → 152 + 4 = 156 = 76 + 80 (배열 끝 다음 주소)

5다단계(multi-level) 배열

zip_vec postech = {3, 7, 6, 7, 3};
zip_vec snu     = {0, 8, 8, 2, 0};
zip_vec kaist   = {3, 4, 1, 4, 1};

#define UCOUNT 3
int *univ[UCOUNT] = {postech, kaist, snu};
  • univ는 포인터(8byte) 원소 3개짜리 배열 → 각 포인터가 int 5개짜리 배열을 가리킴
  • 앞의 nested 배열 pohang은 5개짜리 행 4개가 한 덩어리로 붙어 있었음. 여기서는 행 3개가 따로 선언되어 있고 univ는 그 행들의 시작 주소만 모아 둔 배열
  • 슬라이드 가정 (univ의 시작 주소 160, 원소 간격 8byte):
    • univ[0] = 16 → postech (16~35)
    • univ[1] = 56 → kaist (56~75, 초기화 순서가 {postech, kaist, snu}라 둘째 칸이 kaist)
    • univ[2] = 36 → snu (36~55)
  • 행 시작 주소가 16, 56, 36으로 규칙 없이 흩어져 있음. nested 배열의 행 시작이 늘 간격으로 일정했던 것과 다른 점
  • 포인터만 저장하므로 각 행이 메모리 어디에 있어도 되고 행마다 길이가 달라도 됨
  • 대신 원소를 읽을 때 포인터를 한 번 따라가야 함
int get_univ_digit(size_t index, size_t col) {
    return univ[index][col];     // 슬라이드는 col을 dig(digit)이라고 부름
}
# index in %rdi, col in %rsi
    salq $2, %rsi                # 4*dig
    addq univ(,%rdi,8), %rsi     # p = univ[index] + 4*dig
    movl (%rsi), %eax            # return *p
    ret
  • salq $2, %rsi: col을 왼쪽으로 2칸 shift → 4·col (원소 int 크기 4를 곱한 열 offset)
  • addq univ(,%rdi,8), %rsi: 메모리 univ + 8·index에서 행 포인터 univ[index]를 읽어 열 offset에 더함 → p. scale 8은 포인터 크기 (univ의 원소가 포인터라서)
  • 이 한 명령이 메모리 읽기(첫 번째)와 덧셈을 함께 함
  • movl (%rsi), %eax: p가 가리키는 int를 읽어 반환 (두 번째 메모리 읽기)
  • 슬라이드 정리: 접근 식은 Mem[Mem[univ+8*index]+4*dig] → 메모리 읽기가 두 번 (첫 번째는 목표 행 배열의 포인터, 두 번째는 그 배열 안의 목표 원소)

손계산: nested와 multi-level 원소 접근 비교 (index = 1, col = 2)

  1. nested pohang[1][2] (pohang = 76, 행 하나 20byte): 주소 = 76 + 20·1 + 4·2 = 104 → 메모리 읽기 1번: M[104] = 6 (행 1 = 3 7 6 7 1의 셋째 값)
  2. multi-level get_univ_digit(1, 2) (univ = 160): salq → %rsi = 8 · addq → 160 + 8·1 = 168에서 M[168] = 56 (첫 번째 읽기) → %rsi = 8 + 56 = 64 · movl → M[64] = 1 (두 번째 읽기, kaist의 셋째 값)
  3. univ[2][4]도 같은 순서: M[160 + 16] = M[176] = 36 → 36 + 4·4 = 52 → M[52] = 0 (snu의 마지막 값)
  4. 같은 열 offset 8(= col 2)이어도 행 포인터가 달라 도착하는 곳이 달라짐: univ[0] → 16 + 8 = 24 (값 6) · univ[1] → 56 + 8 = 64 (값 1) · univ[2] → 36 + 8 = 44 (값 8)
최종 답nested: 주소를 산술로만 구해 읽기 1번 · multi-level: 행 포인터를 읽고 원소를 읽어 2번

6N×N 행렬: 고정 크기 vs 가변 크기

행렬 코드의 세 가지 형태

// ① Fixed dimensions — 컴파일 시점에 N을 앎
#define N 16
typedef int fix_matrix[N][N];
int fix_ele(fix_matrix a, int i, int j) { return a[i][j]; }

// ② Variable dimensions, explicit indexing — 동적 배열의 전통적 방법
#define IDX(n, i, j) ((i)*(n)+(j))
int vec_ele(size_t n, int *a, int i, int j) { return a[IDX(n,i,j)]; }

// ③ Variable dimensions, implicit indexing — 지금은 gcc가 지원
int var_ele(size_t n, int a[n][n], int i, int j) { return a[i][j]; }
// i*n+j 계산을 컴파일러가 해 줌. 인자 n이 a보다 앞에 와야 a[n][n]에서 쓸 수 있음

16×16 행렬 접근 (고정 크기)

# a in %rdi, i in %rsi, j in %rdx
    salq $6, %rsi             # 64*i
    addq %rsi, %rdi           # a + 64*i
    movl (%rdi,%rdx,4), %eax  # M[a + 64*i + 4*j]
    ret
  • 원소 주소 에서 C = 16, k = 4 → 한 행이 64byte =
  • salq $6, %rsi: 왼쪽으로 6칸 shift = 64배 → 행 시작까지의 offset
  • N이 컴파일 시점의 상수라 행 크기도 상수 → 곱셈 없이 shift와 덧셈만으로 주소가 나옴

n×n 행렬 접근 (가변 크기)

# n in %rdi, a in %rsi, i in %rdx, j in %rcx
    imulq %rdx, %rdi          # n*i
    leaq (%rsi,%rdi,4), %rax  # a + 4*n*i
    movl (%rax,%rcx,4), %eax  # a + 4*n*i + 4*j
    ret
  • n이 실행 중에 정해짐 → 정수 곱셈(imulq)이 필요: %rdi = n × i (행 번호 × 열 개수)
  • 16×16과 비교: 행 크기 64가 상수일 때는 salq $6, 행 크기 4·n이 변수일 때는 imulq

손계산: 16×16과 n×n의 원소 주소 (a = 0x1000, i = 3, j = 5)

  1. fix_ele(a, 3, 5): salq → %rsi = 3 ≪ 6 = 192 · addq → %rdi = 0x1000 + 192 = 0x10C0 · movl → 주소 0x10C0 + 4·5 = 0x10D4
  2. var_ele(16, a, 3, 5): imulq → %rdi = 48 · leaq → %rax = 0x1000 + 4·48 = 0x10C0 · movl → 주소 0x10D4
  3. 검산: (3 × 16 + 5) × 4 = 212 = 0xD4 → 0x1000 + 0xD4 = 0x10D4. 두 함수가 같은 주소를 읽음
  4. n = 10이면: imulq로 10 × 3 = 30 → 0x1000 + 120 = 0x1078 → 열 offset 20을 더해 0x108C. 검산: (3 × 10 + 5) × 4 = 140 = 0x8C ✓
최종 답주소는 둘 다 a + 4·n·i + 4·j. 행 크기가 상수여야 곱셈을 shift로 바꿀 수 있음

연속 저장 — Row-major (80 Bytes)

선택: A[1][2]

주소 = base + (i × C + j) × sizeof(int)

= 0x0000000000001000 + (1 × 5 + 2) × 4

= 0x0000000000001000 + 28

= 0x000000000000101C

sizeof(A) = 4 × 5 × 4 = 80 B

int* p의 p+1은 4바이트 전진합니다.

int (*)[5] p의 p+1은 20바이트 전진합니다.

7struct: 표현과 멤버 접근

struct rec {
    int a[4];
    size_t i;
    struct rec *next;
};
  • 구조체는 모든 field를 담을 만큼 큰 메모리 block 하나로 표현됨
  • field는 선언한 순서대로 배치됨. 다른 순서가 더 compact한 표현을 만들 수 있어도 순서를 바꾸지 않음
  • 전체 크기와 field 위치는 컴파일러가 정함 → 기계어 수준 프로그램은 소스의 구조체를 이해하지 못함 (남는 것은 offset 숫자뿐)
  • 크기: a 4 × 4 = 16 @0, i(size_t) 8 @16, next(포인터) 8 @24 → 16 + 8 + 8 = 32byte (padding 없음)
  • next는 다음 struct rec의 시작을 가리키는 포인터

멤버 포인터 생성: get_ap

int *get_ap(struct rec *r, size_t idx) {
    return &r->a[idx];    // 각 member의 offset은 컴파일 시점에 결정 → 주소는 r + 4*idx
}
# r in %rdi, idx in %rsi
    leaq (%rdi,%rsi,4), %rax   # base = r, index = idx, scale = 4 (a의 offset이 0)
    ret                        # leaq 하나 — 메모리를 읽지 않고 주소만 계산

set_val: next를 따라가며 a[i]에 쓰기

void set_val(struct rec *r, int val) {
    while (r) {
        int i = r->i;
        r->a[i] = val;
        r = r->next;
    }
}
.L11:                          # loop:  (%rdi = r, %rsi = val)
    movslq 16(%rdi), %rax      # i = Mem[r+16]
    movl %esi, (%rdi,%rax,4)   # Mem[r+4*i] = val
    movq 24(%rdi), %rdi        # r = Mem[r+24]
    testq %rdi, %rdi           # Test r
    jne .L11                   # if !=0 goto loop
  • member 접근이 전부 r에 offset을 더하는 꼴:
    • 16(%rdi) = r->i (offset 16)
    • 24(%rdi) = r->next (offset 24)
    • (%rdi,%rax,4) = r->a[i] (offset 0 + 4·i)
  • r->i는 8byte size_t인데 int i에 담으므로 아래쪽 4byte만 movslq로 읽어 64bit로 부호 확장
  • testq + jne: r이 0이 아니면 다음 node로 loop 계속, 0이면 종료. 슬라이드에는 loop 몸체만 나옴

손계산: set_val 추적 (node 0x1000: i = 1, next = 0x2000 / node 0x2000: i = 3, next = 0, val = 9)

  1. 반복 1 (%rdi = 0x1000): movslq → M[0x1010] = 1 → %rax = 1 · movl → M[0x1000 + 4] = M[0x1004] = 9 · movq → M[0x1018] = 0x2000 → %rdi = 0x2000 · testq → 0 아님 → .L11로 점프
  2. 반복 2 (%rdi = 0x2000): movslq → M[0x2010] = 3 → %rax = 3 · movl → M[0x200C] = 9 · movq → M[0x2018] = 0 → %rdi = 0 · testq → 점프 안 함, 종료

8struct alignment

정렬 원칙

  • Aligned data: 기본 data type이 B byte를 요구하면 주소는 B의 배수. 일부 machine에서는 필수, x86-64에서는 권장
  • type별 요구 B (= type 크기): char 1 · short 2 · int·float 4 · long·double·포인터 8
  • 정렬하는 동기:
    • memory는 (시스템에 따라) 4byte 또는 8byte 단위의 정렬된 chunk로 접근됨
    • quad-word 경계에 걸친 data의 load/store는 비효율
    • virtual memory에서 data가 두 page에 걸치면 더 까다로움
  • compiler가 구조체 안에 gap(padding)을 넣어 각 field의 정렬을 맞춤
구조체 안: 각 element의 정렬 요구 충족 · 구조체 전체: = element들 중 가장 큰 정렬 요구 → 구조체의 시작 주소와 전체 길이가 모두 의 배수

S1: internal padding

S2: 멤버 순서만 바꾸면 padding 위치가 달라짐

9struct 배열과 공간 절약

struct 배열

  • struct S2 a[10];: 구조체 전체 길이는 K의 배수, 그리고 배열의 모든 원소도 정렬 요구 충족
  • a[0]은 a, a[1]은 a+24, a[2]는 a+48 (원소 하나 24byte)
  • 끝쪽 padding 덕분에 다음 원소의 v도 8의 배수에 놓임. 끝 padding이 없으면 원소 크기가 17이 되어 a[1]의 v가 a+17에 놓여 8의 배수가 아님
  • a[1]을 확대하면: v가 a+24, i[0]이 a+32, c가 a+40, 마지막 byte가 a+47

struct S3 {

    float v;
    short j;

# idx in %rdi
    leaq (%rdi,%rdi,2), %rax    # 3*idx
    movzwl a+8(,%rax,4), %eax
    ret
  • sizeof(S3) = 12. alignment spacer(padding)를 포함한 크기. 배열 offset은 12·idx, member j는 구조체 안 offset 8
  • leaq (%rdi,%rdi,2): idx + 2·idx = 3·idx. 12배는 scale에 쓸 수 없어서(1, 2, 4, 8뿐) 3배를 먼저 만들고 movzwl의 scale 4로 12·idx를 완성
  • movzwl a+8(,%rax,4), %eax: 주소 a + 8 + 4·(3·idx) = a + 12·idx + 8에서 short 2byte를 읽어 0으로 채워 %eax에 (movz = zero extend, w = 2byte 원본, l = 4byte 목적지)
  • a+8의 offset 값은 linking 때 정해짐

10Floating point

배경: x87, SSE, AVX

  • x87 FP: legacy 방식
  • SSE (Streaming SIMD Extensions) FP: SIMD = Single Instruction Multiple Data. 명령어 하나로 여러 data를 한꺼번에 처리
  • 오래된 machine이 지원. vector instruction의 특수한 경우로 사용
  • AVX (Advanced Vector Extensions)는 SSE를 확장한 SIMD 명령어 집합이다. x87, SSE, AVX를 비교하면 AVX가 가장 나중에 나온 확장이지만, AVX-512와 같은 후속 확장도 존재하므로 AVX를 현재 가장 최신 버전이라고 일반화해서는 안 된다. 이 강의의 구체적인 부동소수점 명령어 예제는 슬라이드에 맞춰 SSE3 기준으로 이해한다.
  • 슬라이드 32 제목이 "Programming with SSE3" → 이 수업은 SSE3 기준

XMM register

scalar와 SIMD 연산

  • addss %xmm0,%xmm1: scalar, single precision → 낮은 4byte 한 쌍만 더함
  • addps %xmm0,%xmm1: SIMD, single precision → float 4개를 칸끼리 동시에 더함
  • addsd %xmm0,%xmm1: scalar, double precision → 낮은 8byte 한 쌍만 더함
  • 이름 규칙: 앞 add는 덧셈, 가운데 s는 scalar / p는 packed(SIMD), 끝 s는 single / d는 double. AT&T 순서라 결과는 두 번째 인자 %xmm1에 저장

FP 기본: 인자와 반환

FP 값은 XMM register로 전달: 인자는 순서 · 반환값은 · XMM register는 모두 caller-saved
  • callee-saved인 XMM register가 하나도 없으므로, 호출 뒤에도 값이 필요하면 호출하는 쪽이 미리 저장
float fadd(float x, float y) { return x + y; }
double dadd(double x, double y) { return x + y; }
# x in %xmm0, y in %xmm1
    addss %xmm1, %xmm0    # fadd: %xmm0 = x + y — 결과가 곧바로 반환 register에
    ret
    addsd %xmm1, %xmm0    # dadd: single(ss) 대신 double(sd) 명령
    ret

FP 메모리 참조: dincr

double dincr(double *p, double v) {
    double x = *p;
    *p = x + v;
    return x;
}
# p in %rdi, v in %xmm0        # 정수와 포인터는 일반 register, FP 값은 XMM register
    movapd %xmm0, %xmm1        # Copy v — 다음 movsd가 %xmm0을 덮어써 v가 사라지므로 먼저 복사
    movsd (%rdi), %xmm0        # x = *p        (memory → XMM)
    addsd %xmm0, %xmm1         # t = x + v
    movsd %xmm1, (%rdi)        # *p = t        (XMM → memory)
    ret                        # x가 %xmm0에 있어 return x를 위한 명령이 따로 없음
  • XMM register끼리 옮기는 mov(movapd)와 memory ↔ XMM 사이를 옮기는 mov(movsd)는 서로 다른 명령어 (movsd에는 XMM 간 이동 형식도 있으나, 여기서는 128bit 전체 복사에 movapd, 하위 double의 memory 적재/저장에 movsd 사용)

손계산: scalar와 SIMD 덧셈, dincr 추적

  1. float 4칸, %xmm0 = [1.0, 2.0, 3.0, 4.0], %xmm1 = [10.0, 20.0, 30.0, 40.0] (왼쪽이 낮은 칸): addss %xmm0,%xmm1 → %xmm1 = [11.0, 20.0, 30.0, 40.0] (낮은 칸 한 쌍만 10.0 + 1.0)
  2. addps %xmm0,%xmm1 → %xmm1 = [11.0, 22.0, 33.0, 44.0] (네 칸 모두)
  3. 둘은 각각 초기값에서 따로 실행한 결과
  4. double 2칸, %xmm0 = [1.5, 9.0], %xmm1 = [2.0, 7.0]: addsd → %xmm1 = [3.5, 7.0] (낮은 8byte만 2.0 + 1.5, 위쪽 칸은 그대로)
  5. dincr (*p = 1.5, v = 2.0): 시작 %xmm0 = 2.0, M[p] = 1.5 · movapd → %xmm1 = 2.0 · movsd → %xmm0 = 1.5 (x) · addsd → %xmm1 = 3.5 (t) · movsd → M[p] = 3.5 · ret → 반환값 %xmm0 = 1.5 (옛 *p)
최종 답*p는 1.5 → 3.5로 바뀌고, 반환값은 바뀌기 전 값 1.5

11시험 포인트

배열·포인터

  • T N[L]은 연속된 byte, 원소 i의 주소 = 시작 주소 + sizeof(T) · i (char 1, short 2, int 4, long·포인터·double 8)
  • 배열 이름은 첫 원소의 주소: val, val+1, &val[2], val+i는 int *이고 값은 → 포인터에 더하는 정수는 원소 크기만큼 곱해짐
  • *(val+1)은 val[1]의 값
  • 범위 밖 val[5]의 값은 알 수 없음 (C 표준상 UB)
  • Intel은 little endian: int 3은 03 00 00 00으로 저장
  • addl $1, (%rdi,%rax,4) = z[i]++: base = 배열 시작, index = i, scale = 원소 크기, 메모리 값을 직접 갱신
  • for (i = 0; i < 5; i++)는 cmpq $4, %rax + jbe로 컴파일됨 (size_t는 unsigned 비교)

다차원·다단계 배열

  • T N[R][C]: 크기 , row-major 배치, 한 행은 byte
  • 행 시작 주소 = · 원소 주소 =
  • leaq (%rdi,%rdi,4) = 5·index (scale은 1, 2, 4, 8뿐이라 x + 4x로 5배), 이어지는 leaq/movl에서 원소 크기 4를 곱함
  • int *univ[3] 같은 multi-level 배열은 원소 접근에 메모리 읽기 두 번: Mem[Mem[univ+8·index]+4·dig] (행 포인터 → 원소)
  • nested는 주소 계산 후 한 번만 읽음
  • multi-level의 행은 서로 떨어져 있을 수 있음 (예: 16, 56, 36)
  • nested는 행 간격이 항상
  • 고정 크기 int[16][16] 접근은 salq $6 (64·i) + addq + movl
  • 가변 크기 행렬의 주소: int a[n][n]에서 원소 a[i][j]의 주소는 a + 4·n·i + 4·j이다. 먼저 imulq로 행 번호와 열 개수의 곱인 n·i를 계산한다.
  • 명령어 선택: leaq로 행 시작 주소 a + 4·n·i를 계산하고, movl로 4·j만큼 떨어진 위치의 원소를 읽는다. 행 크기가 컴파일 시점에 상수이면 행 offset의 곱셈을 shift로 대체할 수 있지만, 행 크기가 실행 중 결정되면 일반적으로 imulq가 필요하다.

struct·alignment

  • 구조체 field는 선언 순서대로, offset은 컴파일 시점에 정해짐
  • struct rec은 offset 0 / 16 / 24, 크기 32 · &r->a[idx]는 leaq 한 줄
  • 정렬: 기본 type이 B byte를 요구하면 주소는 B의 배수
  • 구조체는 K = field 중 가장 큰 정렬 요구. 시작 주소와 전체 길이가 K의 배수가 되도록 compiler가 internal padding과 끝 padding을 넣음
  • struct S1 {char c; int i[2]; double v;} : offset 0, 4, 16, sizeof 24 (padding 3 + 4)
  • 순서를 바꾼 S2 {double v; int i[2]; char c;} : offset 0, 8, 16, 끝 padding 7 → 크기는 똑같이 24
  • 구조체 배열 원소 a[idx]의 주소 = a + sizeof·idx (padding 포함 크기), member는 거기에 offset을 더함
  • S3는 sizeof 12, j의 offset 8 → leaq (%rdi,%rdi,2) (3·idx) + movzwl a+8(,%rax,4)
  • 공간 절약은 큰 type을 앞에: S4 {char c; int i; char d;} 12byte → S5 {int i; char c; char d;} 8byte

Floating point

  • FP: XMM register는 16개, 각 16byte · 인자는 %xmm0, %xmm1, … · 반환은 %xmm0 · 전부 caller-saved
  • addss·addsd는 scalar(낮은 4 / 8byte 한 쌍), addps는 SIMD(float 4개 동시)
  • FP 값은 XMM register, 정수와 포인터 인자는 일반 register (dincr는 p가 %rdi, v가 %xmm0)
  • 이동 명령어가 다름: XMM끼리는 movapd, memory ↔ XMM은 movsd (movsd에는 XMM 간 이동 형식도 있음)

문제 1. double d[5]의 시작 주소가 0x500일 때 ① 전체 크기 ② &d[3] ③ d+4 ④ 마지막 원소 d[4]가 차지하는 주소 범위를 구하라.

정답 보기
  1. 전체 크기 = 5 × 8 = 40 = 0x28 byte

  3. d+4 = 0x500 + 4 × 8 = 0x500 + 0x20 = 0x520 (double *에 더하므로 원소 크기 8을 곱함)
  4. d[4]는 0x520~0x527 (8byte), 배열 전체는 0x500~0x527
최종 답① 0x28 ② 0x518 ③ 0x520 ④ 0x520~0x527
