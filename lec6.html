Lecture 6 · Machine-Level Programming III — Procedures(프로시저)

10/15 (목) · 녹화 강의슬라이드 "Lecture 6 Procedures" (PDF 38~39, 49~72) + 수업 녹취. PDF 2~37, 40~48, 73~74는 녹화가 없어 슬라이드만 보고 정리

1Procedure(프로시저) 호출에 필요한 것

💡세 가지 메커니즘과 ABI 프로시저(함수)를 부르고 돌아오는 데는 세 가지가 필요:
  • Passing control: 부른 프로시저 code의 시작으로 가고, 끝나면 호출한 자리(return point)로 돌아옴
  • Passing data: 인자(procedure arguments)와 반환값(return value)
  • Memory management: 프로시저가 실행되는 동안 공간을 할당하고, return하면 해제
셋 모두 machine instruction으로 구현되고, x86-64는 필요한 메커니즘만 씀 (인자도 local 변수도 없는 프로시저는 그 부분을 구현하지 않아도 됨). machine instruction으로 어떻게 구현할지는 ABI (Application Binary Interface)가 표준으로 정해 둠.
슬라이드 예제: P가 y = Q(x)로 Q를 부르고 print(y)로 이어감 — Q 안의 local 변수 t와 배열 v[10]은 Q가 실행되는 동안만 필요한 공간.
  • 강의 순서: Stack Structure → Calling Conventions (Passing Control, Passing Data, Managing Local Data) → Recursion & Pointers

2x86-64 stack과 push, pop

stack과 %rsp

  • stack은 stack discipline(LIFO, 나중에 들어간 것이 먼저 나옴)으로 관리하는 memory 영역 — memory는 byte 배열, 영역마다 쓰임이 다름 (ABI 같은 정책 결정)
  • stack은 낮은 주소 쪽으로 자람. %rsp는 stack에서 가장 낮은 주소, 즉 top 원소의 주소를 담음

pushq와 popq

  • pushq src: src의 값을 읽음 → %rsp를 8 줄임 → %rsp가 가리키는 주소에 그 값을 씀
  • popq dst: %rsp가 가리키는 주소에서 값을 읽음 → %rsp를 8 늘림 → 읽은 값을 dst에 저장
  • No cleanup: pop 뒤에도 값은 memory에 남아 있고, %rsp가 어디까지가 유효한 stack인지를 정함
  • 세 동작이 instruction 하나로 실행됨 (atomic single instruction). 8바이트씩 움직이는 것은 q(quad word)가 8바이트이기 때문. push는 %rsp를 먼저 줄이고 쓰고, pop은 먼저 읽고 %rsp를 늘리므로 둘은 서로를 정확히 되돌림

3call과 ret — 제어 이동

예제: multstore와 mult2

void multstore(long x, long y, long *dest) {
    long t = mult2(x, y);
    *dest = t;
}
long mult2(long a, long b) { long s = a * b; return s; }

  400541: mov  %rdx,%rbx        # Save dest
  400544: callq 400550 <mult2>  # mult2(x,y)

  • callq, retq는 call, ret의 disassembler 표기 (q는 64bit)
  • multstore: push %rbx로 저장, mov %rdx,%rbx로 dest 보관, call 뒤 mov %rax,(%rbx)로 결과 저장, pop %rbx로 복원
  • (보충) %rdx는 caller-saved라 call을 넘어 값이 남는다는 보장이 없어서 callee-saved인 %rbx에 dest를 둠
📖call과 ret이 하는 일 call label: return address를 stack에 push하고 label로 점프 — return address = call 바로 다음 instruction의 주소.
ret: stack에서 return address를 pop하고 그 주소로 점프.
✏️손계산 1 · call과 ret에서 %rsp와 %rip (시작: %rsp = 0x120, %rip = 0x400544 = callq 직전)
callq 400550 <mult2> — return address = (다음 줄 주소, callq는 5바이트). %rsp = , [0x118] = 0x400549, %rip = 0x400550
mov %rdi,%rax (0x400550) → %rip = 0x400553 · imul %rsi,%rax (0x400553) → %rip = 0x400557, %rsp는 계속 0x118
retq (0x400557): %rip = [0x118] = 0x400549, %rsp = — call 직전과 %rsp가 같음 (call이 8 줄이고 ret이 8 늘림)
이어서 multstore: mov %rax,(%rbx) (0x400549) → pop %rbx (0x40054c): %rsp = 0x128 → retq (0x40054d): %rsp = 0x130, multstore를 부른 곳으로 복귀

multstore 진입 직후 %rsp = 0x128 ([0x128]에 return address), push %rbx로 0x120, pop %rbx로 0x128 복귀. pop된 0x400549 값은 0x118 칸에 흐리게 남아 있음 (no cleanup).

4인자와 반환값 — Procedure Data Flow

인자 전달: 처음 여섯 개는 register — , 일곱 번째부터는 stack (필요할 때만) · 반환값:
  • multstore: x는 %rdi, y는 %rsi, dest는 %rdx · mult2: a는 %rdi, b는 %rsi — multstore가 받은 x, y가 같은 register에 그대로 있어서 옮기지 않고 바로 call
  • mult2는 a×b를 %rax에 남기고, multstore는 그 값을 받아 mov %rax,(%rbx)로 dest에 저장. dest(%rdx)만 call 전에 %rbx로 옮겨 둠 — %rdx는 call을 넘어 보존된다는 보장이 없기 때문
✏️손계산 2 · mult2의 값 흐름 (x = 6, y = 7 가정)
진입: %rdi = 6 (x), %rsi = 7 (y), %rdx = dest
push %rbx, mov %rdx,%rbx → %rbx = dest (호출자의 %rbx는 stack에 저장)
callq mult2: %rdi, %rsi 그대로 a = 6, b = 7 → mov → %rax = 6 → imul → %rax = → retq
mov %rax,(%rbx): [dest] = 42 (*dest = t) · pop %rbx: 호출자의 %rbx 복원, retq

*dest = x × y = 42

5Stack 기반 언어와 Stack Frame(스택 프레임)

Recursion(재귀)을 지원하는 언어

  • C, Pascal, Java 같은 언어는 code가 re-entrant해야 함: 같은 프로시저의 실행이 동시에 여러 개 진행될 수 있고, 앞선 호출이 끝나기 전에도 안전하게 실행돼야 함 → 각 실행의 상태(인자, local 변수, return pointer)를 둘 자리가 필요
  • Stack discipline: 프로시저의 상태는 호출부터 return까지의 한정된 시간 동안만 필요하고, callee가 caller보다 먼저 return → stack은 frame 단위로 할당, frame 하나 = 프로시저 호출 하나의 상태

frame의 내용과 관리

  • 내용: return 정보, local 저장 공간(필요하면), 임시 공간(필요하면)
  • 관리: 진입 시 할당(set-up code, call이 push한 return address 포함), return 시 해제(finish code, ret이 pop하는 return address 포함)
  • %rsp는 현재 frame의 맨 위, %rbp(frame pointer, optional)는 현재 frame의 아래쪽 경계, 그 아래(높은 주소)에 이전 frame들

6Register(레지스터)를 건드려도 되는가

읽기와 쓰기 — incr 예제

  • register를 읽는 것은 문제없음 (값을 바꾸지 않음). 쓰는 경우에는 프로그램이 깨지지 않는지 따져야 함 — caller와 callee가 제어와 데이터를 주고받는 관계라, 어느 쪽이 register를 바꾸든 상대의 실행이 깨지면 안 됨
incr:
    movq (%rdi), %rax   # x = *p
    addq %rax, %rsi     # y = x + val (%rsi가 val에서 y로 바뀜)
    movq %rsi, (%rdi)   # *p = y
    ret
  • 수정되는 register: %rax(반환값 자리라 당연), %rsi(까다로운 쪽 — call_incr가 넣어 둔 3000을 덮어씀). 이 경우는 괜찮음: call_incr가 call 뒤에 %rsi를 다시 읽지 않기 때문
  • 문제는 callee가 덮어쓴 register를 caller가 return 뒤에 읽을 때 → 아래 yoo/who 예제
✏️손계산 4 · call_incr의 주소와 %rsp (가정: 진입 직전 %rsp = 0x120, [0x120] = return address) 
long call_incr() {
    long v1 = 15213;
    long v2 = incr(&v1, 3000);
    return v1 + v2;
}

7Register 저장 규약 — caller-saved vs callee-saved

💡두 역할로 나눈 보관 책임
  • caller-saved: caller가 call 전에 임시 값을 자기 stack frame에 저장하고 call 뒤에 복원 → callee는 이 register를 제약 없이 덮어써도 됨
  • callee-saved: callee가 register를 쓰기 전에 값을 자기 stack frame에 저장하고 ret 전에 복원 → caller 입장에서는 call 전후로 값이 보존됨. callee가 그 register를 수정할 때만 저장·복원 책임이 생김
다른 방식도 있음: 아주 단순한 architecture는 call 전에 모든 register를 memory에 저장(전부 caller-save), ARM은 shadow register 세트로 통째 복사(교수님도 "맞다면"이라고 조심스럽게 말함, 확인 안 됨). x86은 두 방식을 섞어 register마다 책임을 나눔 — ABI가 정하는 정책이라 architecture마다 다를 수 있음.

왜 이렇게 나뉘는가

  • %rax: 반환값을 돌려주려면 callee가 반드시 덮어씀 → call 뒤에도 필요한 값이 있었다면 caller가 미리 저장
  • 인자 register: callee에게 인자를 넘기려면 caller가 덮어써야 함 → 받은 인자를 다른 호출 뒤에도 써야 한다면 옛 값을 먼저 저장. 그래서 caller 쪽 책임
  • 특별한 의미 없는 임시 register는 책임을 둘로 나눔: %r10, %r11은 caller 쪽, %rbx와 %r12~%r15는 callee 쪽
  • 함수 하나가 caller이면서 callee: 어떤 register는 caller로서 챙기고, 어떤 register는 callee로서 챙김
  • %rsp와 %rbp: stack은 caller/callee 경계에 걸쳐 있음 → frame을 만든 callee가 정리하는 쪽이 자연스러움 (%rsp = 원래 값으로 복구, return address = caller의 context로 복귀)

callee-saved 예제 — call_incr2

long call_incr2(long x) {
    long v1 = 15213;
    long v2 = incr(&v1, 3000);
    return x + v2;
}
  • 문제: x는 %rdi로 들어오고 마지막 x + v2까지 보관돼야 하는데, incr에 첫 인자 &v1을 넘기려면 %rdi를 덮어써야 함. %rdi는 caller-saved라 보장 없음
  • 해결: callee-saved register인 %rbx에 x를 둠 → incr가 %rbx를 쓰더라도 return 전에 복원해 줌. 대신 내가 %rbx를 쓰려면 내 caller의 %rbx를 먼저 저장했다가 복원
call_incr2:
    pushq %rbx          # 내 caller의 %rbx를 stack에 저장
    subq  $16, %rsp     # local 변수 공간 확보
    movq  %rdi, %rbx    # x → %rbx (call을 넘어 보존)
    movq  $15213, 8(%rsp) # v1 = 15213
    movl  $3000, %esi   # 2번째 인자
    leaq  8(%rsp), %rdi # 1번째 인자 &v1
    call  incr
    addq  %rbx, %rax    # x + v2
    addq  $16, %rsp     # 확보한 공간 반환
    popq  %rbx          # 내 caller의 %rbx 복원
    ret
  • (보충) 8바이트만 쓰는데 16을 잡는 이유는 call 시점에 %rsp가 16바이트 경계에 맞아야 하는 ABI 규칙 때문 (수업 범위 밖)
  • 복원은 저장의 역순(LIFO): addq $16, %rsp → popq %rbx → ret. 이때 %rsp가 return address를 가리켜야 ret이 제대로 돌아감
  • 저장·복원 장소에 정해진 한 방법은 없음 — 남는 register를 쓰는 편이 memory보다 빠름 (compiler 최적화)

8Recursion(재귀) — pcount_r

long pcount_r(unsigned long x) {
    if (x == 0) return 0;
    else return (x & 1) + pcount_r(x >> 1);
}
pcount_r:
    movl $0, %eax       # 반환값 = 0 (종료 경로 대비)
    testq %rdi, %rdi    # x & x → x == 0이면 ZF = 1
    je   .L6            # x == 0 → 바로 ret
    pushq %rbx          # callee-saved %rbx 저장
    movq %rdi, %rbx
    andl $1, %ebx       # %rbx = x & 1 (상위 32bit도 0)
    shrq %rdi           # %rdi = x >> 1 (재귀 인자)
    call pcount_r
    addq %rbx, %rax     # (x & 1) + 재귀 결과
    popq %rbx           # %rbx 복원
.L6:
    rep; ret
  • 재귀 호출 때 %rdi가 x >> 1로 바뀌어 나가므로, 끝에서 더할 x & 1은 따로 보관 → callee-saved %rbx
  • x == 0 경로는 %rbx를 건드리지 않으므로 pushq, popq를 건너뜀 (callee-saved는 수정할 때만)
  • rep; ret: AMD 쪽 분기 최적화로 붙인 더미 1바이트 → 정확성과 무관, ret으로 읽어도 됨
  • 호출마다 새 stack frame이 생겨 자기 return address와 자기 Saved %rbx를 따로 가짐 → 재귀 깊이만큼 stack이 자람. 모든 호출이 같은 %rbx를 쓰지만 각 호출이 push/pop으로 복원하므로 서로를 망가뜨리지 않음

호출 A (x = 5): %rdi = 5 ≠ 0 → pushq %rbx ([0x118] = B0), %rbx = 5 & 1 = 1, %rdi = 2, call → [0x110] = R1

9Stack과 호출 규약 정리

💡호출 규약이 보장하는 것 (슬라이드 71) 함수 호출에는 세 가지가 얽혀 있음: 제어 이동, 데이터 이동(인자·반환값), 저장 공간 관리(stack frame) — 슬라이드 2의 세 메커니즘과 같은 축.
  • stack frame: 호출마다 private storage (saved register, local 변수, saved return pointer)
  • register 저장 규약: 한 함수 호출이 다른 함수의 데이터를 망가뜨리지 않게 함 (C 코드가 일부러 그러는 경우는 예외 — Lecture 9의 buffer overflow)
  • stack discipline: P가 Q를 호출하면 Q가 P보다 먼저 return → LIFO. mutual recursion(P ↔ Q)도 같은 규칙으로 처리
핵심은 caller-callee 관계와 context 저장: 인자를 올바르게 다루고, caller가 나중에 쓸 register를 망가뜨리지 않는 것.
  • 슬라이드 요약: 재귀(mutual 포함)도 보통의 호출 규약으로 처리 → local stack frame과 callee-saved register에 값을 안전하게 보관. 인자는 stack top에 두고, 결과는 %rax로. 포인터는 값의 주소(stack 또는 global).
  • local 값은 stack frame에 두되 너무 크게 잡지 않음 — stack은 계속 자라다 다른 영역과 겹칠 수 있음. stack 크기에는 한도가 있음 ((보충) Linux 기본 stack 한도는 ulimit -s 기준 8192 KB = 8 MB; 수업 녹취의 "8K"는 불명확). 지역 변수가 아주 크면 heap(malloc)을 쓰라는 취지로 들림 (녹취 불명확, 확인 안 됨)
  • stack은 다른 데이터 영역과 반대 방향(낮은 주소)으로 자람

10시험 포인트

⭐시험 포인트
  • register를 읽는 것은 안전하고 쓰는 것이 문제: callee가 바꾼 register를 caller가 return 뒤에 다시 읽으면 값이 사라짐 → 보관 책임을 정해 둠
  • caller-saved: caller가 call 전에 자기 frame에 저장하고 call 후 복원, callee는 마음대로 덮어씀 / callee-saved: callee가 쓰기 전에 저장하고 ret 전에 복원
  • caller-saved: %rax, 인자 6개(%rdi %rsi %rdx %rcx %r8 %r9), %r10, %r11 / callee-saved: %rbx, %rbp, %r12~%r15, %rsp는 특수한 형태(나갈 때 원래 값으로)
  • %rax는 반환값이라 callee가 반드시 덮어써서, 인자 register는 인자를 넘기려고 caller가 덮어써서 caller-saved
  • call을 넘어 살아 있어야 하는 값은 callee-saved register(예: %rbx)에 두고, 그 register를 쓰는 함수는 push로 저장하고 pop으로 복원 — 수정할 때만
  • call_incr2 패턴: pushq %rbx → movq %rdi, %rbx → … → addq %rbx, %rax → popq %rbx, 복원은 저장의 역순(LIFO)
  • 저장·복원 장소는 stack만이 아님: 남는 register를 쓰는 편이 memory보다 빠름
  • 재귀: 호출마다 stack frame이 생겨 자기 return address와 Saved %rbx를 가짐, mutual recursion까지 같은 규약
  • pcount_r stack 사용: 종료가 아닌 호출 하나마다 16바이트 (return address 8 + Saved %rbx 8)
  • rep; ret은 ret과 같은 동작, 정확성과 무관한 AMD용 최적화
  • frame 구조: %rsp 쪽부터 Argument Build, Local variables + Saved registers, Old %rbp(optional), Return addr., 7번째 이후 인자(caller frame)
  • stack은 낮은 주소 쪽으로 자라고 %rsp는 top 원소(가장 낮은 주소)의 주소
  • pushq: %rsp를 8 줄이고 씀 / popq: 읽고 %rsp를 8 늘림, pop 뒤에도 값은 memory에 남고 %rsp가 유효한 top을 정함
  • call label: return address(다음 instruction의 주소)를 push하고 점프 / ret: pop하고 그 주소로 점프 → call 직전 %rsp가 S이면 call 직후 S − 8, ret 직후 다시 S
  • 인자 전달: 처음 6개는 %rdi → %rsi → %rdx → %rcx → %r8 → %r9, 7번째부터 stack, 반환값은 %rax
  • 7번째 이후 인자는 caller의 frame에 있음: 진입 직후 8(%rsp), pushq를 할 때마다 offset이 8씩 커짐 (add10은 두 push 뒤 24(%rsp)가 a6)
  • 재귀를 지원하려면 code가 re-entrant해야 하고, 호출마다 인자·local 변수·return pointer를 자기 frame에 둠
  • frame은 진입할 때 할당하고 return할 때 해제, callee가 caller보다 먼저 return해서 LIFO로 충분
  • call chain에서 frame은 호출 깊이만큼 쌓였다가 return하면 풀리고, 해제된 자리는 다음 호출이 다시 씀
  • movl $imm, %esi는 %rsi 상위 32bit를 0으로 만들고 movq보다 1바이트 짧음
  • call_incr 추적: subq $16 → 8(%rsp) = v1 = 15213 → leaq 8(%rsp), %rdi → incr 뒤 v1 = 18213, %rax = 15213 → addq 8(%rsp), %rax = 33426
  • Small Exercise: a0~a5는 register, a6~a9는 stack, add10은 a5(%r9, caller-saved)를 첫 add5 호출 뒤에도 쓰려고 %rbp로 옮기고, callee-saved인 %rbx, %rbp는 push/pop으로 보존
