Procedure(프로시저) 호출에 필요한 것

이 부분은 수업 녹화가 없어 슬라이드만 보고 정리함

세 가지 메커니즘과 ABI (슬라이드 2~3)

프로시저(함수)를 부르고 돌아오는 데는 세 가지가 필요함

  • Passing control : 부른 프로시저 code의 시작으로 가고, 끝나면 호출한 자리(return point)로 돌아옴
    Passing data : 인자(procedure arguments)와 반환값(return value)
    Memory management : 프로시저가 실행되는 동안 공간을 할당하고, return하면 해제함

이 셋은 모두 machine instruction으로 구현되고, x86-64는 필요한 메커니즘만 씀 (슬라이드 : uses only those mechanisms required)

  • (보충) 예 : 인자도 local 변수도 없는 프로시저는 그 부분을 구현하지 않아도 됨

machine instruction으로 어떻게 구현할지는 ABI(Application Binary Interface)가 표준으로 정해 둠 (슬라이드 3)

슬라이드 예제 : P가 y = Q(x)로 Q를 부르고 print(y)로 이어감

  • Q 안의 local 변수 t와 배열 v[10]은 Q가 실행되는 동안만 필요한 공간 → memory management
  • 그림의 화살표 : P에서 Q의 시작으로 가고(passing control), x가 인자로 넘어가고 v[t]가 반환값으로 돌아오며(passing data), Q의 return에서 P의 print(y)로 돌아옴(return point)

슬라이드 4, 9, 19, 22는 강의 순서를 보이는 agenda 슬라이드

  • Stack Structure → Calling Conventions(Passing Control, Passing Data, Managing Local Data) → Illustrations of Recursion & Pointers

x86-64 stack과 push, pop

stack과 %rsp (슬라이드 5)

stack은 stack discipline(LIFO, 나중에 들어간 것이 먼저 나옴)으로 관리하는 memory 영역

  • memory는 byte 배열로 보고, 영역마다 쓰임이 다름 (슬라이드 : ABI처럼 정책 결정)

stack은 낮은 주소 쪽으로 자람

%rsp는 stack에서 가장 낮은 주소, 즉 top 원소의 주소를 담음

슬라이드 그림 : 오른쪽 memory는 위쪽이 낮은 주소(Increasing address 화살표가 아래로 향함), Code 영역이 위에 있고 Stack이 아래에 있음

  • stack top이 위쪽에 그려져 있어서, 값이 쌓일수록 위로(낮은 주소 쪽으로) 자람

pushq와 popq (슬라이드 6~8)

pushq src (슬라이드 6~7 : push 뒤에는 그림에서 (src) 칸이 top 위에 새로 생기고 %rsp가 8 줄어듦)

  • src의 값을 읽음 → %rsp를 8 줄임 → %rsp가 가리키는 주소에 그 값을 씀

popq dst (슬라이드 8 : %rsp += 8)

  • %rsp가 가리키는 주소에서 값을 읽음 → %rsp를 8 늘림 → 읽은 값을 dst에 저장
  • No cleanup : pop 뒤에도 값은 memory에 남아 있고, %rsp가 어디까지가 유효한 stack인지를 정함 (슬라이드 8 그림에서 흐리게 남은 (src) 칸)

슬라이드 제목의 "Atomic Single Instruction" : push와 pop은 위 세 동작이 instruction 하나로 실행됨

(보충) 8바이트씩 움직이는 것은 q(quad word)가 8바이트이기 때문, push는 %rsp를 먼저 줄이고 쓰고 pop은 먼저 읽고 %rsp를 늘리므로 둘은 서로를 정확히 되돌림

call과 ret : 제어 이동

이 부분은 수업 녹화가 없어 슬라이드만 보고 정리함

예제 코드 : multstore와 mult2 (슬라이드 10)

void multstore(long x, long y, long *dest) {
    long t = mult2(x, y);
    *dest = t;
}

long mult2(long a, long b) {
    long s = a * b;
    return s;
}
0000000000400540 <multstore>:
  400540: push   %rbx              # Save %rbx
  400541: mov    %rdx,%rbx         # Save dest
  400544: callq  400550 <mult2>    # mult2(x,y)
  400549: mov    %rax,(%rbx)       # Save at dest
  40054c: pop    %rbx              # Restore %rbx
  40054d: retq                     # Return
  ...
0000000000400550 <mult2>:
  400550: mov    %rdi,%rax         # a
  400553: imul   %rsi,%rax         # a * b
  400557: retq                     # Return

multstore가 mult2를 부르고, 슬라이드의 callq, retq는 call, ret의 disassembler 표기 ((보충) 접미사 q는 64bit)

mult2 : %rdi(a)를 %rax에 옮기고 %rsi(b)를 곱해 %rax에 남긴 뒤 retq

multstore : push %rbx로 %rbx를 저장, mov %rdx,%rbx로 dest를 %rbx에 보관, call 뒤 mov %rax,(%rbx)로 결과를 dest에 저장, pop %rbx로 복원, retq

  • (보충) %rdx는 caller-saved라 call을 넘어 값이 남는다는 보장이 없어서, callee-saved인 %rbx에 dest를 둠 (뒤의 call_incr2와 같은 패턴)

call과 ret이 하는 일 (슬라이드 11)

stack으로 procedure call과 return을 구현함

call label : return address를 stack에 push하고 label로 점프

  • return address = call 바로 다음 instruction의 주소

ret : stack에서 return address를 pop하고 그 주소로 점프

call 한 번 : %rsp와 %rip (슬라이드 12~15)

슬라이드 12 (call 직전) : %rip = 0x400544 (다음에 실행할 instruction이 callq), %rsp = 0x120

슬라이드 13 (push) : return address 0x400549를 push → %rsp = 0x118, [0x118] = 0x400549, 이 슬라이드에서 %rip는 아직 0x400544로 그려져 있음

슬라이드 14~15 (jump) : %rip = 0x400550 (mult2의 첫 instruction), %rsp = 0x118 그대로

(보충) %rip가 callq(0x400544)에 있으므로 그 앞의 push %rbx는 이미 실행된 뒤이고, 슬라이드의 %rsp = 0x120은 그 push 뒤의 값

ret 한 번 : %rsp와 %rip (슬라이드 16~18)

슬라이드 16 : mult2 안에서 %rip = 0x400557 (retq), %rsp = 0x118, stack top에 return address 0x400549

슬라이드 17~18 (ret 뒤) : %rip = 0x400549, %rsp = 0x120 → multstore의 mov %rax,(%rbx)부터 이어서 실행

  • 0x400549 값은 0x118 칸에 흐리게 남아 있음 (pop과 같은 no cleanup)

슬라이드의 값 그대로 %rsp = 0x120, %rip = 0x400544(callq 직전)에서 시작

① callq 400550 <mult2> : return address = ((보충) 슬라이드의 주소 열에서 다음 줄이 0x400549라서 callq는 5바이트)

  • %rip = 0x400550

② mov %rdi,%rax (0x400550) → %rip = 0x400553

(보충) 이어서 multstore가 끝날 때까지

⑤ mov %rax,(%rbx) (0x400549) → %rip = 0x40054c

⑥ pop %rbx (0x40054c) : %rsp = 0x128, %rip = 0x40054d

⑦ retq (0x40054d) : %rsp = 0x130, multstore를 부른 곳으로 돌아감

  • multstore에 들어온 직후 %rsp = 0x128 ([0x128]에 return address), push %rbx로 0x120이 되고 pop %rbx로 0x128로 돌아옴

인자와 반환값 : Procedure(프로시저) Data Flow

이 부분은 수업 녹화가 없어 슬라이드만 보고 정리함

인자 register와 반환값 (슬라이드 20~21)

인자 전달 : 처음 여섯 개는 register, 일곱 번째부터는 stack (필요할 때만)

  • register 순서 : %rdi → %rsi → %rdx → %rcx → %r8 → %r9

반환값 : %rax

슬라이드 21은 슬라이드 10의 예제에 인자 위치를 주석으로 단 것

  • multstore : x는 %rdi, y는 %rsi, dest는 %rdx
  • mult2 : a는 %rdi, b는 %rsi → multstore가 받은 x, y가 같은 register에 그대로 있어서 옮기지 않고 바로 call
  • mult2는 a * b를 %rax에 남기고(a * b → %rax), multstore는 mult2(x,y) → %rax로 그 값을 받아 mov %rax,(%rbx)로 dest에 저장
  • (보충) dest(%rdx)만 call 전에 %rbx로 옮겨 둠 : %rdx는 call을 넘어 보존된다는 보장이 없기 때문

손계산 2 : mult2의 값 흐름

(보충) 슬라이드에는 값이 없어서 x = 6, y = 7로 가정, dest는 결과를 받을 long 변수의 주소

① 진입 : %rdi = 6 (x), %rsi = 7 (y), %rdx = dest

② push %rbx, mov %rdx,%rbx : %rbx = dest (호출자의 %rbx는 stack에 저장됨)

③ callq mult2 : %rdi, %rsi가 그대로 a = 6, b = 7

  • mov %rdi,%rax → %rax = 6
  • imul %rsi,%rax → %rax =
  • retq

④ mov %rax,(%rbx) : [dest] = 42 (*dest = t)

⑤ pop %rbx : 호출자의 %rbx를 복원하고 retq

검산 : *dest = x × y = 42

stack 기반 언어와 stack frame

이 부분은 수업 녹화가 없어 슬라이드만 보고 정리함

Recursion(재귀)를 지원하는 언어 (슬라이드 23)

재귀를 지원하는 언어 : C, Pascal, Java 같은 것

  • code가 re-entrant해야 함 : 같은 프로시저의 실행이 동시에 여러 개 진행될 수 있고, 앞선 호출이 끝나기 전에도 안전하게 실행돼야 함
  • 그래서 각 실행의 상태(인자, local 변수, return pointer)를 둘 자리가 필요함

Stack discipline

  • 프로시저의 상태는 호출부터 return까지의 한정된 시간 동안만 필요함
  • callee가 caller보다 먼저 return함

Stack은 frame 단위로 할당 : frame 하나가 프로시저 호출 하나(instantiation)의 상태

stack frame의 내용과 관리 (슬라이드 24)

frame의 내용 : return 정보, local 저장 공간(필요하면), 임시 공간(필요하면)

관리

  • 프로시저에 들어갈 때 공간을 할당 : set-up code, call이 push한 return address도 여기에 포함
  • return할 때 해제 : finish code, ret이 pop하는 return address도 포함

그림 : %rsp는 현재 frame의 맨 위, %rbp(frame pointer, optional)는 현재 frame의 아래쪽 경계를 가리키고, 그 아래에 이전 frame들이 쌓여 있음

call chain 예제 : yoo, who, amI (슬라이드 25)

세 프로시저 : yoo가 who()를 부르고, who가 amI()를 두 번 부르고, amI는 자기 자신을 부르는 재귀 프로시저

Example Call Chain

  • yoo → who → amI → amI → amI : who가 부른 amI가 amI를 부르고, 그 amI가 다시 amI를 부름 (재귀)
  • who → amI : who의 두 번째 amI() 호출 (그림에서 이 amI는 더 부르지 않음)

x86-64/Linux stack frame (슬라이드 37)

Caller의 frame 쪽에 있는 것

  • return address : call이 push함
  • callee에게 넘기는 7번째 이후 인자 (있을 때만)

Callee(현재) frame에 있는 것

  • Argument build(optional) : 이제 부를 함수에 넘길 parameter를 만들어 두는 자리
  • Local variables : register에 둘 수 없을 때 쓰는 자리
  • Saved register context : 저장해 둔 register
  • Old frame pointer(optional) : 이전 %rbp

그림 : %rsp는 Argument Build 맨 위, %rbp는 Old %rbp를 가리키고, 그 아래의 Return addr.와 7+th Arguments가 Caller Frame으로 묶임

  • 같은 그림을 슬라이드 72가 다시 요약함 → 아래 "stack frame 구조와 크기"

(보충) 7번째 이후 인자는 caller가 call 전에 stack에 두므로 return address보다 높은 주소에 있음, callee에 들어온 직후에는 7번째 인자가 8(%rsp) → 연습문제 9의 add10이 이 경우

register를 건드려도 되는가

읽기와 쓰기, incr 예제

register를 읽는 것은 문제가 없음 : 값을 바꾸지 않으므로 상태가 그대로

register에 쓰는(값을 갱신하는) 경우에는 프로그램이 깨지지 않는지 따져야 함

  • 함수를 부른 쪽(caller)은 호출이 끝나면 제어를 돌려받고 그 register를 계속 쓸 수 있음
    caller와 callee가 제어와 데이터를 주고받는 관계라서, 어느 쪽이 register를 바꾸든 상대의 실행이 깨지면 안 됨
incr:
    movq   (%rdi), %rax    # x = *p
    addq   %rax, %rsi      # y = x + val  (%rsi가 val에서 y로 바뀜)
    movq   %rsi, (%rdi)    # *p = y
    ret

register 사용 : %rdi = 인자 p (읽기만 함), %rsi = 인자 val → y, %rax = x → 반환값

수정되는 register는 두 개 : %rax, %rsi

  • %rax : 반환값을 담는 자리라서 callee가 쓰는 게 당연함 → caller는 반환값을 받으려고 %rax를 읽음
    %rsi : 까다로운 쪽. call_incr가 movl $3000, %esi로 넣어 둔 값을 incr가 y로 덮어씀
    이 경우는 괜찮음 : call_incr가 call 뒤에 %rsi를 다시 읽지 않기 때문 (뒤에 오는 코드는 addq 8(%rsp), %rax뿐)

문제는 callee가 덮어쓴 register를 caller가 return 뒤에 읽을 때 생김 → 다음 예제

call_incr 한 줄씩 추적 : 인자 준비까지 (슬라이드 40~44)

이 부분은 수업 녹화가 없어 슬라이드만 보고 정리함

슬라이드 39의 표(%rdi, %rsi, %rax의 Use(s))는 처음에 모두 XX이고, 한 줄 실행할 때마다 채워짐 ((보충) XX는 아직 의미 있는 값이 없다는 뜻으로 읽음)

슬라이드 40 subq $16, %rsp : %rsp가 16바이트 내려가 8바이트 칸 두 개가 생김

  • 이 시점의 표 : %rdi = &v1, %rsi = 3000, %rax = XX → incr(&v1, 3000)의 인자 두 개가 준비됨

Register(레지스터) 저장 규약

caller-saved와 callee-saved

해결책 : register 보관 책임을 두 역할로 나눔

caller-saved : caller가 call 전에 임시 값을 자기 stack frame에 저장하고, call 뒤에 복원

  • callee는 이 register를 제약 없이 덮어써도 됨

callee-saved : callee가 register를 쓰기 전에 값을 자기 stack frame에 저장하고, ret 전에 복원

  • caller 입장에서는 이 register의 값이 call 전후로 보존됨
  • callee가 그 register를 수정할 때만 저장·복원 책임이 생김 (수업 : "when it's modified")

다른 방식도 있음 (수업에서 언급, 슬라이드에는 없음)

  • 아주 단순한 architecture : call 전에 모든 register를 memory에 저장함 (전부 caller-save)
  • ARM : 주 register 세트와 shadow register 세트를 두고 호출 전에 통째로 복사한다고 설명함 (교수님도 "맞다면"이라고 조심스럽게 말함, 확인 안 됨)
  • x86은 두 방식을 섞어서 register마다 책임을 나눔

이런 분담은 ABI가 정하는 정책 결정이라 architecture마다 다를 수 있음

x86-64 Linux register 분류

%rax : 반환값, caller-saved
%rdi %rsi %rdx %rcx %r8 %r9 : 인자, caller-saved

%r10 %r11 : caller-saved (특별한 용도가 없는 임시 register)
%rbx %r12 %r13 %r14 %r15 : callee-saved
%rbp : callee-saved, frame pointer로 쓸 수도 있음
%rsp : callee-saved의 특수한 형태, 함수에서 빠져나올 때 원래 값으로 복구됨

caller-saved = callee가 마음대로 바꿔도 되는 register → call 뒤에 값이 남아 있다고 믿으면 안 됨
callee-saved = call을 가로질러 값이 남는 register → callee가 쓰려면 저장해 두었다가 복원해 줌

왜 이렇게 나뉘는가

%rax : 반환값을 돌려주려면 callee가 반드시 덮어씀

  • call 뒤에도 필요한 값이 %rax에 있었다면 caller가 미리 stack 같은 곳에 저장해 둬야 함

인자 register : callee에게 인자를 넘기려면 caller가 덮어써야 함

  • 내가 caller에게서 받은 인자를 다른 함수 호출 뒤에도 써야 한다면, 호출용 인자로 덮어쓰기 전에 옛 값을 저장해야 함
  • 그래서 인자 register는 caller 쪽 책임

특별한 의미가 없는 임시 register는 책임을 둘로 나눔

  • %r10, %r11은 caller 쪽, %rbx와 %r12~%r15는 callee 쪽

함수 하나가 caller이면서 callee : 어떤 register는 caller로서 챙기고, 어떤 register는 callee로서 챙김

  • register 저장은 caller 관점일 수도 callee 관점일 수도 있고, 어느 register를 수정하느냐에 따라 갈림

%rsp와 %rbp : callee가 정리하는 것

stack은 caller와 callee의 경계에 걸쳐 있어서 까다로움

stack 그림을 그려 가며 설명했고, 함수 호출 하나(context)마다 stack frame 하나가 대응됨

호출이 끝날 때 callee가 정리해야 하는 것

  • %rsp와 %rbp를 caller의 stack frame 기준으로 되돌림
  • instruction pointer(return address)를 caller의 context로 되돌려, caller가 call 다음 명령부터 이어서 실행하게 함

frame을 만든 callee가 정리하는 쪽이 자연스러움 → %rsp는 callee-saved의 특수한 형태(함수를 나갈 때 원래 값으로), %rbp도 callee-saved

callee-saved 예제 : call_incr2

문제 : x를 어디에 보관할 것인가

long call_incr2(long x) {
    long v1 = 15213;
    long v2 = incr(&v1, 3000);
    return x + v2;
}

x는 %rdi로 들어오고, 마지막 x + v2까지 보관돼야 함

register 충돌 : incr에 첫 인자 &v1을 넘기려면 %rdi를 덮어써야 함

  • %rdi는 caller-saved라서 call을 넘어 값이 남는다는 보장이 없음

call을 가로질러 x를 어디에 둘 것인가?

  • callee-saved register인 %rbx에 x를 둠 → incr가 %rbx를 쓰더라도 return 전에 복원해 줌
  • 대신 내가 %rbx를 쓰려면, 내 caller의 %rbx를 먼저 저장했다가 복원해 줘야 함

코드 한 줄씩

call_incr2:
    pushq  %rbx              # 내 caller의 %rbx를 stack에 저장
    subq   $16, %rsp         # local 변수 공간 확보
    movq   %rdi, %rbx        # x → %rbx (call을 넘어 보존)
    movq   $15213, 8(%rsp)   # v1 = 15213
    movl   $3000, %esi       # 2번째 인자
    leaq   8(%rsp), %rdi     # 1번째 인자 &v1
    call   incr
    addq   %rbx, %rax        # x + v2  (%rax = incr의 반환값 v2)
    addq   $16, %rsp         # 확보한 공간 반환
    popq   %rbx              # 내 caller의 %rbx 복원
    ret

pushq %rbx : 이 함수가 %rbx를 덮어쓸 것이므로 callee-saved 규칙대로 caller의 %rbx를 stack에 저장

  • 수업 : 어떤 함수든 caller이면서 callee → call_incr2는 incr에게는 caller, 자기를 부른 함수에게는 callee

subq $16, %rsp : v1을 둘 공간 확보, 8(%rsp)에 v1을 둠 (슬라이드 그림의 15213)

  • (보충) 8바이트만 쓰는데 16을 잡는 이유는 call 시점에 %rsp가 16바이트 경계에 맞아야 하는 ABI 규칙 때문, 수업에서는 다루지 않음

movq %rdi, %rbx : x를 %rbx로 옮겨 둠 → 이제 %rdi는 인자 전달에 마음대로 써도 됨

movl $3000, %esi, leaq 8(%rsp), %rdi : 2번째 인자 3000, 1번째 인자 &v1

  • (보충) movl로 써도 %rsi의 상위 32bit는 0이 됨

call incr 뒤 : %rax = incr의 반환값(v2), %rbx에는 x가 그대로 남아 있음

addq %rbx, %rax : 계산

addq $16, %rsp → popq %rbx → ret : 들어올 때의 역순 (LIFO), 이때 %rsp가 return address를 가리켜야 ret이 제대로 돌아감

저장·복원에는 정해진 하나의 방법이 없음 : stack을 쓸 수도, 비어 있는 다른 register를 쓸 수도 있음 → compiler 최적화에 달림

  • 가능하면 register를 쓰는 편이 좋음 : register ↔ register 이동이 register ↔ memory 이동보다 훨씬 빠름

손계산 6 : call_incr2(100)의 stack과 register

가정 : x = 100, 진입 직전 %rsp = 0x120이고 [0x120]에 return address(R0)가 있음 (슬라이드 그림의 Ret. Addr.), 내 caller의 %rbx = B0

진입 : %rsp = 0x120, %rdi = 100

① pushq %rbx : %rsp = 0x118, [0x118] = B0

② subq $16, %rsp : %rsp = 0x108 (16바이트 확보)

③ movq %rdi, %rbx : %rbx = 100

④ movq $15213, 8(%rsp) : [0x110] = 15213 → v1의 주소는

⑤ movl $3000, %esi : %rsi = 3000

⑥ leaq 8(%rsp), %rdi : %rdi = 0x110 (&v1)

⑦ call incr : %rsp = 0x100, [0x100] = call 다음 줄(addq %rbx, %rax)의 주소

  • incr 안 : movq (%rdi), %rax → %rax = 15213
  • addq %rax, %rsi → %rsi =
  • movq %rsi, (%rdi) → [0x110] = 18213 (v1이 바뀜)
  • ret → %rsp = 0x108

⑧ addq %rbx, %rax : %rax =

⑨ addq $16, %rsp : %rsp = 0x118

⑩ popq %rbx : %rbx = [0x118] = B0 (복원), %rsp = 0x120

⑪ ret : %rsp = 0x128 (return address를 꺼냄), 반환값 %rax = 15313

검산 : 반환값 = x + (incr가 돌려준 원래 *p) =

  • v1은 18213으로 바뀌지만 반환식 x + v2에는 쓰이지 않음
  • push 8 + sub 16 = 24바이트를 썼다가 ⑨ ⑩에서 모두 돌려줌 → ⑪ 직전 %rsp = 0x120

Recursion(재귀) : pcount_r

코드와 register 역할

수업 설명 : popcount는 word 안의 1 비트 개수를 세는 함수 (Day 6의 pcount와 같은 문제), 실제로는 반복문 버전이 낫지만 재귀 함수를 이해하려고 재귀 버전으로 바꿔 봄

long pcount_r(unsigned long x) {
    if (x == 0)
        return 0;
    else
        return (x & 1) + pcount_r(x >> 1);
}

x == 0이면 셀 1이 없음 → 0 반환 (재귀 종료)

아니면 LSB가 1인지(x & 1) 더하고, 나머지 윗부분(x >> 1)은 같은 함수로 재귀

재귀 호출 때 %rdi가 x >> 1로 바뀌어 나가므로, 끝에서 더할 x & 1은 따로 보관해야 함 → callee-saved %rbx

pcount_r:
    movl   $0, %eax        # 반환값 = 0 (종료 조건 경로를 위해 미리)
    testq  %rdi, %rdi      # x & x → x == 0이면 ZF = 1
    je     .L6             # x == 0 → 바로 ret
    pushq  %rbx            # callee-saved %rbx 저장
    movq   %rdi, %rbx
    andl   $1, %ebx        # %rbx = x & 1
    shrq   %rdi            # %rdi = x >> 1 (재귀 인자)
    call   pcount_r
    addq   %rbx, %rax      # (x & 1) + 재귀 결과
    popq   %rbx            # %rbx 복원
.L6:
    rep; ret

testq, je : 앞에서 본 if-else 분기와 같음 → x == 0이면 .L6로 점프, 이때 %rax = 0이 이미 반환값

  • x == 0 경로는 %rbx를 건드리지 않으므로 pushq, popq를 건너뜀 (callee-saved는 수정할 때만)

movq %rdi, %rbx, andl $1, %ebx : x의 LSB를 %rbx에 보관

  • (보충) andl은 32bit 목적지라 상위 32bit가 0이 되어 %rbx 전체가 x & 1

shrq %rdi : 재귀 인자 x >> 1 준비

addq %rbx, %rax : 재귀 호출이 돌려준 윗부분의 1 개수에 내 LSB를 더함

rep; ret : 수업 설명으로는 AMD 쪽 컴파일러 최적화로 분기를 조금 더 빠르게 하려고 붙인 더미 1바이트 → 정확성과 무관, ret으로 읽어도 됨

Recursion(재귀) 호출 한 단계

call 직전 상태 (슬라이드 Call Setup) : %rdi = x >> 1 (재귀 인자), %rax = 반환값 자리, %rbx = x & 1 (callee-saved)

  • stack (슬라이드 그림은 위쪽이 낮은 주소) : Ret. Addr. 위에 Saved %rbx가 push되어 %rsp가 Saved %rbx를 가리킴

재귀 호출에서 돌아오면 %rax에 윗부분의 1 개수가 들어 있음 → addq %rbx, %rax로 내 몫(x & 1)을 더함

popq %rbx : %rbx가 Saved %rbx(내 caller의 값)로 복원되고, rep; ret으로 %rsp는 이 호출의 Ret. Addr.를 넘어 caller 쪽으로 돌아감 (슬라이드 Completion)

호출마다 새 stack frame이 생겨 자기 return address와 자기 Saved %rbx를 따로 가짐 → 재귀 깊이만큼 stack이 자람

모든 호출이 같은 %rbx를 쓰지만 각 호출이 push/pop으로 복원하므로 서로의 값을 망가뜨리지 않음

손계산 7 : pcount_r(5)

5 = 101b → 1 비트 2개, 기대 결과 2

가정 : 첫 호출 진입 시 %rsp = 0x120, [0x120] = main으로 돌아갈 주소(R0), 호출자의 %rbx = B0, R1 = pcount_r 안 call 다음 줄(addq %rbx, %rax)의 주소

호출 A (x = 5) : %rdi = 5 ≠ 0 → pushq %rbx ([0x118] = B0), %rbx = 5 & 1 = 1, %rdi = 2, call → [0x110] = R1

호출 B (x = 2) : 진입 %rsp = 0x110, pushq → [0x108] = 1 (A의 %rbx), %rbx = 2 & 1 = 0, %rdi = 1, call → [0x100] = R1

호출 C (x = 1) : 진입 %rsp = 0x100, pushq → [0xf8] = 0 (B의 %rbx), %rbx = 1 & 1 = 1, %rdi = 0, call → [0xf0] = R1

호출 D (x = 0) : 진입 %rsp = 0xf0, %rax = 0, testq로 ZF = 1 → je .L6 → ret (push 없음) → %rsp = 0xf8, %rax = 0

  • 가장 깊을 때 : 바이트 (A, B, C가 각각 saved %rbx 8 + return address 8)

되감기

  • C로 복귀 : addq %rbx, %rax → %rax = 0 + 1 = 1, popq %rbx → %rbx = [0xf8] = 0, %rsp = 0x100, ret → %rsp = 0x108
  • B로 복귀 : %rax = 1 + 0 = 1 (%rbx는 B의 값 0), popq → %rbx = [0x108] = 1, ret → %rsp = 0x118
  • A로 복귀 : %rax = 1 + 1 = 2 (%rbx는 A의 값 1), popq → %rbx = [0x118] = B0, %rsp = 0x120, ret → %rsp = 0x128

결과 : %rax = 2 → 101b의 1 비트 개수와 일치

각 호출이 보관한 %rbx : A = 1, B = 0, C = 1 (5의 비트를 LSB부터), D는 건드리지 않음 → 합

stack과 호출 규약 정리

호출 규약이 보장하는 것

수업 정리 : 함수 호출에는 세 가지가 얽혀 있음

  • 제어 이동(control transfer), 데이터 이동(인자·반환값), 저장 공간 관리(stack frame) → 슬라이드 2의 Passing control / Passing data / Memory management와 같은 축

특별한 처리 없이 보장되는 것 (슬라이드 71)

  • stack frame : 호출마다 private storage를 가짐 (saved register, local 변수, saved return pointer)
  • register 저장 규약 : 한 함수 호출이 다른 함수의 데이터를 망가뜨리지 않게 함 (C 코드가 일부러 그러는 경우는 예외, 예 : Lecture 9의 buffer overflow)
  • stack discipline : P가 Q를 호출하면 Q가 P보다 먼저 return → LIFO

mutual recursion(P가 Q를 부르고 Q가 P를 부름)도 같은 규칙으로 처리됨

수업 : 한 번 부르든, 재귀든, ping-pong처럼 서로 부르든 상관없음

  • stack 관리 관점에서는 지금 실행 중인 호출이 자기 frame 안에 머물고, 끝나면 caller로 안전하게 돌아가면 됨
  • 핵심은 caller-callee 관계와 context 저장 : 인자를 올바르게 다루고, caller가 나중에 쓸 register를 망가뜨리지 않는 것

stack frame 구조와 크기

(낮은 주소)
%rsp →  Argument Build (Optional)
        Local variables + Saved registers
%rbp →  Old %rbp (Optional)
        Return addr.        ┐
        7+th Arguments      ├ Caller Frame
        ...                 ┘
(높은 주소)

슬라이드 요약 : stack은 call/return에 알맞은 자료구조, P가 Q를 부르면 Q가 P보다 먼저 return

  • 재귀(mutual 포함)도 보통의 호출 규약으로 처리 → local stack frame과 callee-saved register에 값을 안전하게 보관할 수 있음
  • 인자는 stack top에 두고, 결과는 %rax로 돌려줌
  • 포인터는 값의 주소 (stack 또는 global의 값)

local 값은 stack frame에 두되 너무 크게 잡지 않음 : stack은 계속 자라다 다른 영역과 겹칠 수 있음

  • stack 크기에는 한도가 있음 : 수업에서 "8K"라고 말함 (ASR이 불명확), (보충) Linux 기본 stack 한도는 ulimit -s 기준 8192 KB = 8 MB
  • 지역 변수가 아주 많거나 크면 stack 대신 heap에 할당하라는 취지로 들림 ((보충) malloc, 녹취가 불명확해 확인 안 됨)
  • stack은 다른 주 데이터 영역과 반대 방향으로 자람 (stack은 낮은 주소 방향으로 자람, 슬라이드 5)

시험 포인트

register를 읽는 것은 안전하고 쓰는 것이 문제 : callee가 바꾼 register를 caller가 return 뒤에 다시 읽으면 값이 사라지므로 보관 책임을 정해 둠

caller-saved : caller가 call 전에 자기 frame에 저장하고 call 후 복원, callee는 마음대로 덮어씀

callee-saved : callee가 쓰기 전에 저장하고 ret 전에 복원, caller 입장에서 call 전후 값이 같음

caller-saved : %rax, 인자 6개(%rdi %rsi %rdx %rcx %r8 %r9), %r10, %r11

callee-saved : %rbx, %rbp, %r12~%r15, %rsp는 특수한 형태(함수를 나갈 때 원래 값으로 복구)

%rax는 반환값이라 callee가 반드시 덮어써서, 인자 register는 callee에게 인자를 넘기려고 caller가 덮어써서 caller-saved

call을 넘어 살아 있어야 하는 값은 callee-saved register(예 : %rbx)에 두고, 그 register를 쓰는 함수는 push로 저장하고 pop으로 복원

callee-saved register는 수정할 때만 저장·복원 (pcount_r은 x == 0 경로에서 pushq %rbx를 건너뜀)

call_incr2 패턴 : pushq %rbx → movq %rdi, %rbx → ... → addq %rbx, %rax → popq %rbx, 복원은 저장의 역순(LIFO)

한 함수는 caller이면서 callee : callee-saved 저장은 자기 caller를 위한 것, call을 넘어 값을 지키는 것은 자기 callee에게 기대는 것

저장·복원 장소는 stack만이 아님 : 남는 register를 쓰는 편이 memory보다 빠름 (compiler 최적화)

재귀 : 호출마다 stack frame이 생겨 자기 return address와 Saved %rbx를 가짐, 같은 규약으로 mutual recursion까지 처리

pcount_r stack 사용 : 종료가 아닌 호출 하나마다 16바이트 (return address 8 + Saved %rbx 8)씩 쌓임

rep; ret은 ret과 같은 동작, 정확성과 무관한 AMD용 최적화

frame 구조 : %rsp 쪽부터 Argument Build, Local variables + Saved registers, Old %rbp(optional), Return addr., 7번째 이후 인자(caller frame)

stack은 낮은 주소 쪽으로 자라고, %rsp는 top 원소(가장 낮은 주소)의 주소

pushq src : %rsp를 8 줄이고 그 주소에 씀, popq dst : 읽고 %rsp를 8 늘림, pop 뒤에도 값은 memory에 남고 %rsp가 유효한 top을 정함

call label : return address(call 바로 다음 instruction의 주소)를 push하고 label로 점프, ret : return address를 pop하고 그 주소로 점프 → call 직전 %rsp가 S이면 call 직후 S - 8, ret 직후 다시 S

인자 전달 : 처음 6개는 %rdi → %rsi → %rdx → %rcx → %r8 → %r9, 7번째부터 stack, 반환값은 %rax

7번째 이후 인자는 caller의 frame에 있음 : 진입 직후 8(%rsp), pushq를 할 때마다 8씩 커짐 (add10은 두 push 뒤 24(%rsp)가 a6)

재귀를 지원하려면 code가 re-entrant해야 하고, 호출마다 인자·local 변수·return pointer를 자기 frame에 둠

frame은 진입할 때(set-up code, call이 push한 return address) 할당하고 return할 때(finish code, ret이 pop한 return address) 해제, callee가 caller보다 먼저 return해서 LIFO로 충분함

call chain에서 frame은 호출 깊이만큼 쌓였다가 return하면 풀리고, 해제된 자리는 다음 호출이 다시 씀 (yoo → who → amI 3겹 → who → amI)

movl $imm, %esi는 %rsi 상위 32bit를 0으로 만들고 movq보다 1바이트 짧음

call_incr 추적 : subq $16 → 8(%rsp) = v1 = 15213 → leaq 8(%rsp), %rdi → incr 뒤 v1 = 18213, %rax = 15213 → addq 8(%rsp), %rax = 33426

Small Exercise : a0~a5는 %rdi %rsi %rdx %rcx %r8 %r9, a6~a9는 stack, add10은 a5(%r9, caller-saved)를 첫 add5 호출 뒤에도 쓰려고 %rbp로 옮기고, callee-saved인 %rbx, %rbp는 push/pop으로 보존

문제 5

pcount_r(6)에서 ① 호출 횟수(최초 호출 포함) ② 호출마다 %rbx에 보관되는 x & 1 ③ 첫 진입 시점보다 가장 깊을 때 stack이 더 쓰는 바이트 수 ④ 반환값을 구하라.

답

6 = 110b → x = 6, 3, 1, 0 → ① 4번

② x = 6 : 0, x = 3 : 1, x = 1 : 1 (x = 0 호출은 %rbx를 건드리지 않음)

③ 종료가 아닌 호출 3번 × 16바이트 (saved %rbx 8 + return address 8) = 48바이트

④ 되감기 : 0 → 0 + 1 = 1 → 1 + 1 = 2 → 2 + 0 = 2 → 반환값 2

문제 6

문제 7

답

callee-saved register는 callee가 값을 수정할 때만 저장·복원하면 됨 → 이 경로는 %rbx를 건드리지 않으므로 push/pop이 필요 없음

문제 8
