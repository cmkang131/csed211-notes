Bit(비트)와 Byte(바이트)

Everything is Bits(모든 것은 비트)

  • bit : 0 또는 1, 저장 가능한 가장 작은 정보 단위 (논리적으로 0 = False, 1 = True)

  • 왜 2진수인가 → 전기적 구현이 쉬움
    • 아날로그 전압을 low 구간 / high 구간으로 나눠 0 · 1로 해석 (예: DRAM cell의 충전 상태를 주기적으로 refresh)
    • 구간(range)으로 판정하므로 노이즈 · 전압 흔들림이 있어도 안정적으로 decode 가능 (소자가 심하게 마모되지 않는 한)

  • Boolean algebra의 성질이 그대로 성립, 예: De Morgan

C의 Bitwise Operator(비트 연산자)

  • &, |, ~, ^ : 모든 integral 타입(long, int, short, char, unsigned …)에 적용, 인자를 비트 벡터로 보고 bitwise 적용
  • char 예
    • ~0x41 = ~01000001 → 10111110 = 0xBE
    • ~0x00 = ~00000000 → 11111111 = 0xFF
    • 0x69 & 0x55 = 01101001 & 01010101 → 01000001 = 0x41
    • 0x69 | 0x55 = 01101001 | 01010101 → 01111101 = 0x7D
  • hex ↔ binary 변환 요령 : 4비트씩 잘라 각각 변환 (0x41 → 0100 | 0001)

Logical Operator(논리 연산자) && || !

  • 값 전체를 True/False 하나로 축약 : 0만 False, 0이 아니면(양수든 음수든) True
  • 결과는 항상 0 또는 1
    • !0x41 → 0x00 : nonzero → True → NOT → 0
    • !0x00 → 0x01 : 0 → False → NOT → 1
    • !!0x41 → 0x01 : 원래 값 0x41이 아니라 1이 나옴
    • 0x69 && 0x55 → 0x01 : True && True
    • 0x69 || 0x55 → 0x01 : True || True
  • && vs &, || vs | 혼동은 C에서 흔한 실수
    • 예 : 0x69 & 0x55 = 0x41 이지만 0x69 && 0x55 = 0x01

Shift(시프트) 연산

  • left shift x << y : 왼쪽으로 y칸 이동, 왼쪽으로 넘친 비트는 버림, 오른쪽은 0으로 채움
  • right shift x >> y : 오른쪽으로 y칸 이동, 오른쪽으로 넘친 비트는 버림
    • logical shift : 왼쪽을 0으로 채움 (값의 의미는 고려 안 함)
    • arithmetic shift : 왼쪽을 MSB 복제로 채움
  • 수치적 의미 : 왼쪽 1칸 = ×2, 왼쪽 k칸 = / 오른쪽 1칸 = ÷2
    • signed 정수에서 MSB는 음수 weight → 음수를 2로 나눠도 음수여야 하므로 MSB가 1이면 1로 채워야 함 (arithmetic shift의 이유)
  • undefined behavior : shift 양이 0보다 작거나 word size 이상일 때 → 기계마다 다름
    • exception을 내기도, 음수를 아주 큰 양수로 해석하기도 함 → shift는 보수적으로 사용

Integer Representation(정수 표현) : Unsigned(부호 없음)와 Two's Complement(2의 보수)

Encoding(인코딩) 공식

  • 비트
  • unsigned : 모든 위치가 양의 weight , 켜진 비트의 weight를 합산
  • two's complement : 하위 비트 weight는 unsigned와 동일, MSB만 음의 weight
  • sign bit : MSB, 0이면 nonnegative, 1이면 negative
    • MSB 하나만으로 음수가 보장되는 이유 :
    • 하위 비트를 전부 켜도() MSB의 절댓값보다 1 작음 → MSB가 켜지면 무조건 음수

왜 Sign-Magnitude(부호-절댓값)가 아니라 Two's Complement(2의 보수)인가

  • 직관적 대안 : MSB = 부호, 나머지 = 크기 (예 4비트 : 0011 = +3, 1011 = −3)
  • 문제 ①
    • 0000 = +0, 1000 = −0 → 0이 두 개, 패턴 낭비
  • 문제 ②
    • 덧셈 하드웨어가 복잡 : 부호가 같으면 더하고, 다르면 크기를 비교해 큰 쪽에서 작은 쪽을 빼고 큰 쪽의 부호를 붙여야 함 → adder와 별도 subtractor 필요
  • two's complement : 양수 · 음수 조합 상관없이 같은 adder로 그냥 더하면 정답 → 하드웨어 면적 · 에너지 절약
    • 뺄셈도 , → subtractor 불필요
  • (보충) 교수는 "MSB = 부호 + 하위 = 크기" 방식을 one's complement로 부르기도 했는데, 엄밀히는 이것이 sign-magnitude이고 one's complement는 음수를 전체 비트 반전으로 표현하는 방식임. 둘 다 ±0 문제가 있음

C에서의 Signed(부호 있음) / Unsigned(부호 없음)

  • 상수 : 기본은 signed, 접미사 U가 붙으면 unsigned (0U, 4294967259U)
  • explicit casting : T2U / U2T와 동일 (비트 유지)
int tx, ty;
unsigned ux, uy;
tx = (int) ux;       // explicit
uy = (unsigned) ty;  // explicit
tx = ux;             // implicit (대입)
uy = ty;             // implicit (대입)
  • implicit casting : 대입, 함수 호출(procedure call)에서도 자동 발생
    • 예 : signed로 짠 코드에서 unsigned를 받는 라이브러리 함수를 호출하거나 unsigned 반환값을 받을 때
  • C는 이런 변환의 책임을 프로그래머에게 넘김 (Java, Python 같은 고수준 언어는 이런 복잡함이 적음)

Casting Surprise(캐스팅 주의점)

  • 규칙 : 한 식 안에 signed와 unsigned가 섞이면 signed가 unsigned로 implicit cast
    • 산술 연산뿐 아니라 비교 연산 <, >, ==, <=, >=에도 적용
  • w = 32 : TMin = −2,147,483,648, TMax = 2,147,483,647
  • 상수 1 · 관계 · 상수 2 → 해석 방식, 이유
    • 0 == 0U → unsigned : 둘 다 0
    • −1 < 0 → signed : 평범한 비교
    • −1 > 0U → unsigned : −1 → UMax
    • 2147483647 > −2147483648 → signed : TMax > TMin
    • 2147483647U < −2147483648 → unsigned : TMin → >
    • −1 > −2 → signed : 평범한 비교
    • (unsigned) −1 > −2 → unsigned : UMax > UMax − 1
    • 2147483647 < 2147483648U → unsigned :
    • 2147483647 > (int) 2147483648U → signed : (int) = TMin
  • 슬라이드 표에는 "−1 vs (unsigned) −2"와 "(int) 2147383648U"로 적혀 있음 (후자는 2147483648U의 오타로 보임). 어느 쪽이든 관계는 동일 : (unsigned)−2 = 4294967294 < 4294967295 = (unsigned)−1 이므로 −1 쪽이 큼
  • 교수 강조 : −1 vs 0U → 직관상 −1이 작지만 C에서는 −1이 UMax가 되어 더 큼

Extension(확장)과 Truncation(절단)

Sign Extension(부호 확장)

  • 목표 : 비트 signed 를 같은 값을 갖는 비트 로
  • 규칙 : 부호 비트 를 개 복사해 앞에 붙임
  • unsigned 확장(zero extension) : 앞을 0으로 채우면 값 유지 (전부 양의 weight)
  • signed에서 음수를 0으로 채우면 → 양수로 바뀌어 의미 붕괴 → MSB 복사 필요
  • C는 작은 타입 → 큰 타입 변환 시 자동으로 sign extension

    • Truncating (예 int → short) : unsigned는 상위 비트 버림 = mod, signed는 상위 비트 버림 후 재해석 (mod 유사) → 작은 수에서만 기대한 값

Two's Complement Addition(2의 보수 덧셈)

  • overflow 가능성은 부호 조합으로 판단 (교수 강조)

  • carry가 나갔다고 signed 결과가 틀린 것은 아님 (예 : −1 + −1 = 1111 + 1111 = 1 1110 → 1110 = −2, 정상)

Memory(메모리)에서의 표현

Byte-Oriented Memory(바이트 중심 메모리)

  • 프로그램은 virtual address 사용 : 메모리를 아주 큰 byte 배열로 간주 (실제와 다르지만 그렇게 생각해도 됨)
    • address = 배열 index, pointer 변수 = address를 저장
  • 시스템은 프로세스마다 private address space 제공
    • process = 실행 중인 프로그램
    • 자기 데이터는 망가뜨릴 수 있어도 다른 프로세스 데이터는 접근 불가 (OS의 보호, virtual memory가 보장, 이후 강의)

Machine Word(머신 워드)

  • word size : 정수 데이터의 명목상 크기, 더 정확히는 address 크기
    • CPU 레지스터 폭과 일치 (32-bit 기계 = 32비트 레지스터), program counter 같은 레지스터가 메모리 주소를 가리킴
  • 32-bit (4 bytes) : 주소 공간 bytes = 4 GiB (예전엔 충분, 지금 서버에는 부족)
  • 64-bit : 이론상 bytes = 16 EiB ≈ bytes
    • 슬라이드에는 "18 PB, 18.4 × 10^15"로 적혀 있으나 이므로 18 EB가 맞음 (교수도 녹취에서 exabyte로 설명)
    • 실제로는 64비트 전부를 주소로 쓰지 않음 : 하위 일부(교수 설명 45~47비트 수준)만 주소, 상위는 flag 등에 사용 → 실용 한계 약 256 TB ( bytes에 해당)
  • 기계는 여러 데이터 포맷 지원 : word의 분수 · 배수, 항상 정수 바이트

Word-Oriented Memory(워드 중심 메모리)

  • address는 byte 위치를 지정, word의 address = word의 첫 바이트 address
  • 연속된 word의 address 차이 : 4 (32-bit), 8 (64-bit)
    • 32-bit word : 0x0000 → 바이트 0000~0003, 0x0004 → 0004~0007, 0x0008 → 0008~000B, 0x000C → 000C~000F
    • 64-bit word : 0x0000 → 바이트 0000~0007, 0x0008 → 0008~000F
  • 4바이트 word 주소는 하위 2비트가 항상 00, 8바이트 word 주소는 하위 3비트가 항상 000
    • 이 하위 비트들은 word 안에서 몇 번째 byte인지 가리키는 offset으로 사용 (예 : word 0x1000의 첫 byte offset 00, 둘째 byte offset 01)

Byte Ordering(바이트 순서) · Endianness(엔디언)

  • multi-byte word 안의 byte를 메모리에 어떤 순서로 놓을까
  • Big Endian : most significant byte가 가장 낮은 address (Sun, PowerPC Mac, IBM, Internet)
  • Little Endian : least significant byte가 가장 낮은 address (x86, Android · iOS · Windows를 돌리는 ARM)
  • 암기법 : Little endian = Least significant byte at Lowest address
  • ARM은 설정 가능하지만 사실상 little endian, 오늘날 little endian이 de facto
  • Internet(네트워크 전송)만 big endian → 송신 측에서 big endian으로 바꿔 보내고 수신 측에서 다시 little endian으로 변환

손계산 10 : 0x01234567 at 0x100

  • Big Endian : 0x100 → 01, 0x101 → 23, 0x102 → 45, 0x103 → 67
  • Little Endian : 0x100 → 67, 0x101 → 45, 0x102 → 23, 0x103 → 01
  • least significant byte = 0x67 → little endian에서 0x100에 위치
  • big endian은 사람이 쓰는 순서 그대로 왼쪽부터 배치

Little Endian(리틀 엔디언)의 장점 (교수 설명)

  • ① 확장 : 4바이트 word → 8바이트 word로 옮길 때
    • little endian : LSB가 이미 앞에 있음 → 그대로 복사 후 뒤에 0 padding
    • big endian : 값이 MSB 쪽 위치로 가야 하므로 byte를 옮겨야 함
  • ② 연결(concat)도 little endian이 쉬움, big endian은 순서를 재배치해야 함
  • ③ 부분 읽기 : word 안에 1바이트나 2바이트만 저장돼 있어도 little endian은 항상 같은 시작 주소에서 필요한 길이만큼만 신호를 켜서 읽음
    • big endian은 저장 크기에 따라 시작 위치가 달라짐 → 하드웨어를 에너지 효율적으로 만들기에 little endian이 유리
  • 사람에게는 big endian이 직관적이지만, two's complement처럼 기계에게 효율적인 쪽을 택한 것
